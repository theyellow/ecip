Epic 42 — Three Architectural Approaches

How to structure vendor key management + enrichment pipeline

A

New microservice: knowledge-enrichment-service

A dedicated service owns all connector logic, scheduling, and (optionally) key storage. knowledge-engine calls it for enrichment results.

Pros

  • Single responsibility, clear boundary
  • Independent scaling and deployment
  • Easy to add new connectors without touching other services

Cons

  • Another service to run, monitor, deploy
  • Overhead for what starts as a small feature
  • Key management still needs a home (admin-api or here)
B

Extend knowledge-engine

All connector logic, scheduling, and key resolution live inside knowledge-engine. Admin-api exposes CRUD for keys (stored in shared DB).

Pros

  • No new service — simpler ops
  • knowledge-engine already has full access to the knowledge graph
  • Direct ingestion without cross-service calls

Cons

  • knowledge-engine grows in scope (connector + query + ingestion)
  • Harder to scale connector work independently of query work
C

Split responsibility: keys in admin-api, connectors in knowledge-engine ⭐

admin-api owns key CRUD (already manages tenant config). knowledge-engine owns connectors + scheduling + ingestion, reads keys via shared DB table.

Pros

  • Keys sit naturally alongside other tenant config in admin-api
  • No new service; leverages existing architecture
  • Clean separation: admin-api = config plane, knowledge-engine = data plane
  • UI changes are minimal additions to existing admin pages

Cons

  • knowledge-engine still grows (but less than option B)
  • knowledge-engine reads key table directly — mild coupling to admin-api's schema

⭐ Recommended: Option C — matches how the project already separates config from data processing
