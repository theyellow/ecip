== Quick Start

*Prerequisites:* Java 21+, Docker Desktop, Maven 3.9+.

[source,bash]
----
# 1. Clone
git clone <repo-url>
cd emcip

# 2. Build (skip tests for speed)
mvn install -DskipTests

# 3. Start infrastructure
docker compose up -d postgres kafka zookeeper

# 4. Run a service (example: admin-api)
mvn spring-boot:run -pl emcip-admin-api
----

The admin-api starts on port 9087. Health check: `curl http://localhost:9087/actuator/health`.

NOTE: For the complete Docker Compose setup including all profiles and port assignments, see the _Operations Guide_.

NOTE: Docker Compose is the recommended local development environment (see above).
Kubernetes deployment via Helm is for staging and production environments.
See the _Operations Guide_ for the full Kubernetes setup instructions.

NOTE: For the architectural context of these services, see the _Architecture Guide_.

== Module Structure

The project is a Maven multi-module build with a single parent POM (`community-intelligence-parent:0.1.0-SNAPSHOT`).

[cols="2,1,3"]
|===
|Module |Type |Owns

|`emcip-core`
|Library
|Shared: `CommonKafkaConfig`, `TenantContext`, `TenantAwareKafkaSupport`, base event classes, common utilities.

|`emcip-tdlib-adapter`
|Service
|TDLib integration, raw message ingestion, `telegram.raw.messages` producer.

|`emcip-conversation-context`
|Service
|Chat / User / Message entities, thread tracking, `context.threads` producer.

|`emcip-intent-classifier`
|Service
|Intent classification via NLP, `messages.classified` producer.

|`emcip-policy-engine`
|Service
|Policy rule evaluation, versioned rules, `policies.decisions` producer.

|`emcip-llm-orchestrator`
|Service
|LLM provider routing via LiteLLM proxy (OpenAI-compatible); provider URL runtime-configurable via Admin UI, `responses.generated` producer.

|`emcip-moderation-service`
|Service
|Keyword/regex/length rule enforcement, `moderation.flags` producer.

|`emcip-audit-service`
|Service
|Append-only audit log, aggregates events from all topics.

|`emcip-admin-api`
|Service
|REST management API (tenants, policy rules, audit, auth). Also called "Controller" in module context — the sole management entry point; delegates to domain services via REST proxy clients, never via shared DB.

|`emcip-knowledge-engine`
|Service
|Ontology-driven knowledge management; graph (Apache AGE) + vector (pgvector) search, `knowledge.raw.messages` consumer, `knowledge.events` producer.

|`emcip-admin-ui`
|Service
|Spring Boot wrapper serving the React SPA on port 14009.

|`gatling-tests`
|Test module
|Gatling 3.11 load simulations. Excluded from standard `mvn test`. Run via `cd gatling-tests && mvn gatling:test`.
|===

== Development Patterns

=== Service Data Isolation (Mandatory)

Each service owns its own database tables. No service may read or write another service's tables — not even within the same PostgreSQL instance.

[cols="1,3"]
|===
|Need |Pattern to use

|Pipeline event (fire-and-forget, async)
|Produce to a Kafka topic. Consumer service persists in its own tables.

|Management query (synchronous, operator-triggered)
|Implement a REST endpoint on the owning service. Have `emcip-admin-api` call it via a typed `WebClient` proxy (e.g. `ModerationServiceClient`).

|Shared reference data (e.g. tenant config)
|`emcip-admin-api` owns the `tenants` table; other services receive tenant context via Kafka header (`X-Tenant-Id`) or HTTP header — they do not query the tenants table directly.
|===

IMPORTANT: If you are tempted to inject a repository from another service's module, stop. Add a REST endpoint to the owning service and call it via `WebClient` with `X-Service-Token`.

`admin-api` accepts an inbound `X-Service-Token` **only** on `/api/internal/**` (reserved for internal callbacks); a valid token on any other `/api/**` path is rejected with 403. Actuator endpoints are open for scraping (not token-gated), matching the other services.

=== JPA Entities (Phase 2/3 services)

Every JPA entity follows this pattern:

[source,java]
----
@Entity
@Table(name = "my_entity")
@Data
@NoArgsConstructor
public class MyEntity {

    @Id
    @GeneratedValue(strategy = GenerationType.UUID)
    @Column(nullable = false, updatable = false)
    private UUID id;

    @Version
    private Long version;          // optimistic locking

    @Column(nullable = false)
    private String name;

    @Column(nullable = false)
    private UUID tenantId;         // row-level tenant isolation

    @CreatedDate
    @Column(nullable = false, updatable = false)
    private Instant createdAt;

    @LastModifiedDate
    private Instant updatedAt;
}
----

Key rules:

* UUID primary keys, never `BIGSERIAL`.
* `@Version` on every entity for optimistic locking.
* `@Column(nullable = false)` on every non-null column — never rely on database defaults.
* Use Lombok `@Data` + `@NoArgsConstructor` — never write manual getters/setters.
* Enable `@EnableJpaAuditing` on the `@SpringBootApplication` class for `@CreatedDate`/`@LastModifiedDate`.

=== Kafka Producers and Consumers

All Kafka configuration inherits from `CommonKafkaConfig` in `emcip-core`:

[source,java]
----
// Producing an event
@RequiredArgsConstructor
@Service
public class MessagePublisher {

    private final KafkaTemplate<String, Object> kafkaTemplate;

    public void publish(TelegramRawMessageEvent event) {
        kafkaTemplate.send("telegram.raw.messages", event.getEventId().toString(), event);
    }
}
----

[source,java]
----
// Consuming events
@Slf4j
@Service
public class MessageConsumer {

    @KafkaListener(topics = "telegram.raw.messages", groupId = "intent-classifier")
    public void consume(TelegramRawMessageEvent event) {
        log.info("Received event: {}", event.getEventId());
        // process...
    }
}
----

*DLQ pattern:* Failed messages after retry exhaustion are routed to `<topic>.dlq` by `CommonKafkaConfig`. Monitor via Kafka UI (port 14004).

*Tenant propagation:* Use `TenantAwareKafkaSupport` when producing — it adds the `tenant_id` header automatically from `TenantContext`.

=== Liquibase Migrations

Every service has one master changelog at `src/main/resources/db/changelog/db.changelog-master.xml`.

[source,xml]
----
<!-- db.changelog-master.xml -->
<databaseChangeLog xmlns="http://www.liquibase.org/xml/ns/dbchangelog"
                   xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
                   xsi:schemaLocation="http://www.liquibase.org/xml/ns/dbchangelog
                   http://www.liquibase.org/xml/ns/dbchangelog/dbchangelog-4.0.xsd">
    <include file="db/changelog/2026-04-15-1-initial-schema.xml"
             relativeToChangelogFile="false"/>
    <!-- Add new changesets here. Never modify existing ones. -->
</databaseChangeLog>
----

Individual changeset naming: `YYYY-MM-DD-N-description.xml`.

Rules:

* *Never Flyway* — this project uses Liquibase exclusively.
* Never modify a committed changeset — always add a new one.
* For a new column: `<addColumn>`, not `<modifyColumn>`.
* Include `<rollback>` tags for destructive operations.

=== Spotless Formatting

Run before every commit:

[source,bash]
----
mvn spotless:apply
----

Expected output: `0 were changed to be clean` (the zero is the important number — it means no files needed formatting).

If files were changed: `git add -A && git commit --amend --no-edit`.

CI enforces `mvn spotless:check` in the `verify` phase. A failing Spotless check blocks the build.

=== Coverage gate

`mvn verify` enforces a per-module JaCoCo line-coverage floor across all 11 Java modules, measured
on merged unit + integration test execution data. Floors ratchet up (`measured − 2`) as coverage
improves and may never be lowered without a written reason. See `docs/development/coverage.md` for
the current floors, the rules, and how to re-measure.

=== Admin UI: context identity and request loops

Pages follow one shape: `useAuthRequest()` → `useMemo` an api client on it → `useCallback` a loader on the client → `useEffect` the loader. That is a "load once on mount" only if the request keeps its identity between renders. If it does not, every `setState` re-arms the effect, which fetches, which sets state again — an unbounded request loop.

`useAuthRequest` used to call `makeRefreshableRequest(...)` on every render, so it never did. The loop was invisible while it merely hammered the API; it became a visible outage once per-caller rate limiting landed, as a burst of hundreds of requests that drained the caller's bucket and turned every page into 429s until the state stopped changing. The rate limiter did not cause it — it exposed it.

Consequently *everything `AuthProvider` hands out is memoized*: the callbacks with `useCallback`, the context value with `useMemo`, and the request with `useMemo` over the values that actually change what it sends. Preserve that when editing `AuthContext`, and prefer `renderHook` identity assertions plus a "one mount, one fetch" test (`AuthContext.test.jsx`) over eyeballing the network tab — the loop self-terminates once the error text stops changing, so it is easy to mistake for a transient glitch.

=== Error Responses: what may reach a client (admin-api)

Exception messages are internal diagnostics. They name database schema, classes, packages and file paths, and must not be echoed to an HTTP client — a real leak shipped this way (a Telegram reconnect returned the fail-closed crypto error verbatim, disclosing `telegram_accounts.api_hash` and a repo path).

`GlobalExceptionHandler` enforces this. Two rules when adding an endpoint:

. *Never put `ex.getMessage()` into a response body.* Log it — with the stack trace — and return a fixed sentence. This applies to a `Map.of("reason", e.getMessage())` in a controller just as much as to a `ProblemDetail`; the leak that prompted this was the former, and it bypassed the advice entirely.
. *To show a client a specific sentence, use one of the two supported routes:* bean validation (`@Valid`, which yields per-field errors) or `ResponseStatusException(status, reason)`, whose reason is author-written. A bare `IllegalArgumentException` is *not* one of them — its detail is replaced with "Invalid request", because in practice such exceptions come from library code (`Enum.valueOf` discloses package and class names, `UUID.fromString` echoes header values).

Where a client genuinely needs to branch on the failure, add a stable `code` property to the `ProblemDetail` rather than making it match on wording — as `SECRET_NOT_ENCRYPTED` does. The admin-ui client surfaces `detail` as the error message and `code` alongside it.

The same contract holds behind the proxy. llm-orchestrator answers the plaintext-secret condition with the identical 409 and `SECRET_NOT_ENCRYPTED` code (`SecretExceptionHandler`), so a caller sees one shape regardless of which service noticed. Note that it has to walk the cause chain to do so: the exception is raised inside a Hibernate attribute converter, which wraps it in a `JpaSystemException` whose own message is the useless "Error attempting to apply AttributeConverter". Matching on the declared exception type alone silently misses it, and the caller gets a bare 500.

=== Reading encrypted columns (JPA services)

A `@Convert`-ed column decrypts *eagerly, on entity load*. One row whose value predates encryption therefore fails every query that materialises the entity — including queries that never wanted the secret.

That is not a theoretical concern: it took out the provider-config list *and* the provider-config edit at once, which are exactly the two screens an operator needs to replace the bad key. The feature that repairs the row was unreachable because of the row it was meant to repair.

*Rule: an administrative read must not decrypt a secret it does not use.* In practice:

* List and detail screens select an interface projection that exposes only whether a key is set, never the key (`LlmProviderConfigRepository.Summary`).
* Writes that must work on a broken row go through `@Modifying` queries. The converter *does* apply to a bound parameter, so the replacement is still stored encrypted — asserted directly against the raw column in `LlmProviderConfigRepositoryIT`, since a silent regression to plaintext would otherwise look exactly like a working feature.
* Never compare an encrypted attribute to a literal in JPQL (`where c.apiKey = '…'`, `like 'v1:%'`). Hibernate converts the *literal*, so the comparison is against fresh ciphertext and can never match. Predicates that need no literal (`is null`) are safe.

=== Rate Limiting (admin-api)

Every admin-api endpoint is rate-limited *per caller*, not globally. A caller that exceeds its limit gets:

[source,http]
----
HTTP/1.1 429 Too Many Requests
Retry-After: 60
Content-Type: application/problem+json

{"type":"about:blank","title":"Too Many Requests","status":429,"detail":"Rate limit exceeded"}
----

[cols="1,2,1,1"]
|===
|Group |Paths |Key |Limit

|`auth`
|`/api/auth/**`, `/auth/**`
|Client IP
|10 / 60s

|`llm-trigger`
|`POST /api/flags/*/analyse`, `POST /api/flags/*/chat`, `POST /api/simulate/message`
|JWT subject
|20 / 60s

|`admin-crud`
|everything else under `/api/**`
|JWT subject
|600 / 60s
|===

`/actuator/**` and `/api/internal/**` are exempt.

IMPORTANT: `admin-crud` is a catch-all, so *a new `/api/**` endpoint is rate-limited by default* — you do not add anything to get it, and you cannot opt out per endpoint. If a new endpoint is expensive enough to need the tighter `llm-trigger` budget, add its path to `RateLimitGroups.resolve`. Do not reach for `RateLimiterOperator` in a controller: per-controller limiters were removed in P3.6 because they counted globally, and mixing the two would double-count every request.

Enforcement lives in `RateLimitWebFilter`, not in the controllers, and it writes the 429 itself — `GlobalExceptionHandler` cannot see exceptions thrown from a `WebFilter`. Details and tuning: `docs/operations/rate-limiting.md`.

== Testing

=== How tests are split and run

Surefire runs unit tests; Failsafe runs integration tests. The split is by **class name**, configured in the root `pom.xml`:

[cols="1,2,2"]
|===
|Plugin |Runs |Phase

|`maven-surefire-plugin`
|`**/*Test.java` — excluding `*IT` and `*IntegrationTest`
|`test`

|`maven-failsafe-plugin`
|`**/*IT.java` and `**/*IntegrationTest.java`
|`integration-test` + `verify`
|===

Because of that split, **`mvn test` does not run integration tests — use `mvn verify`**. The same applies to the admin-ui vitest suite, which is bound to the `test` phase via `frontend-maven-plugin` and skipped by `-DskipTests`.

[source,bash]
----
mvn test      # unit tests only (Surefire)
mvn verify    # unit + integration (Failsafe, needs Docker) + frontend vitest
----

CI runs `mvn -B verify`, so every `*IT` / `*IntegrationTest` class gates the build automatically — adding one requires no CI change.

NOTE: Failsafe must stay listed in the root `<build><plugins>`. It is not a default-lifecycle plugin, so configuring it in `pluginManagement` alone silently disables every integration test.

=== Testcontainers (Integration Tests)

Services with database operations use `TestcontainersInitializer` to spin up a real PostgreSQL container:

[source,java]
----
@SpringBootTest
@ContextConfiguration(initializers = TestcontainersInitializer.class)
class PolicyEngineIntegrationTest {

    @Autowired
    private PolicyRuleRepository policyRuleRepository;

    @Test
    void shouldEvaluateActiveRule() {
        // Arrange — insert rule using real DB
        var rule = new PolicyRuleConfig();
        rule.setName("spam-block");
        rule.setAction("BLOCK");
        rule.setActive(true);
        policyRuleRepository.save(rule);

        // Act
        var decision = policyEvaluationService.evaluate("SPAM", "tenantA");

        // Assert
        assertThat(decision.getDecision()).isEqualTo("BLOCK");
    }
}
----

== TDLib Integration

=== Why TDLib (not Bot API)

EMCIP connects as a *real Telegram user*, not a bot. This provides access to private groups, full message history, and member lists — capabilities unavailable via the Bot API.

=== Docker Build

The TDLib adapter builds TDLib from source inside Docker. The first build takes 15–30 minutes. Subsequent builds use the Docker layer cache.

[source,bash]
----
# Build tdlib-adapter image (runs from repo root)
docker compose build tdlib-adapter

# Or with no-cache to force recompile
docker compose build --no-cache tdlib-adapter
----

=== Authentication

Required environment variables:

[source,bash]
----
TELEGRAM_API_ID=<your-api-id>
TELEGRAM_API_HASH=<your-api-hash>
TELEGRAM_PHONE_NUMBER=+<country><number>
----

Obtain `API_ID` and `API_HASH` from https://my.telegram.org. On first startup, TDLib prompts for the SMS verification code via stdin.

=== Troubleshooting `UnsatisfiedLinkError`

If the service throws `java.lang.UnsatisfiedLinkError: libtdjni.so: cannot open shared object file`, the native library was not compiled or is in the wrong path.

[source,bash]
----
# Rebuild from scratch
docker compose build --no-cache tdlib-adapter

# Verify the .so file is present
docker compose run --rm tdlib-adapter ls /usr/local/lib/libtdjni.so
----

== GraalVM Native Image Development

Three services support native image compilation: `emcip-policy-engine`, `emcip-conversation-context`, and `emcip-llm-orchestrator`.
Native images start in ~1-2 seconds and require no JVM.

NOTE: For production deployments, native images are built automatically by GitHub Actions
(`.github/workflows/build-images.yml`) and pushed to `ghcr.io/theyellow/ecip`.
You only need to build native images locally if you are developing or testing native-image-specific code.

=== Installing GraalVM (Ubuntu 22.04 / 24.04)

GraalVM Community Edition is available via snap on Ubuntu:

[source,bash]
----
# Install GraalVM CE (includes native-image)
sudo snap install graalvm-jdk --classic

# Set JAVA_HOME for the current shell
export JAVA_HOME=/snap/graalvm-jdk/current/graalvm-ce
export PATH=$JAVA_HOME/bin:$PATH

# Verify
java -version        # GraalVM CE 25.x.x
native-image --version
----

TIP: Add the `export` lines to your shell profile (`~/.bashrc` or `~/.zshrc`) to make them permanent.
However, for day-to-day JVM development you may want to keep JDK 21 as the default and only switch to GraalVM when building native images.

=== Building a Native Image

[source,bash]
----
# Switch to GraalVM
export JAVA_HOME=/snap/graalvm-jdk/current/graalvm-ce
export PATH=$JAVA_HOME/bin:$PATH

# Build native binary (takes ~15-20 minutes per service)
mvn -Pnative package -DskipTests -pl emcip-policy-engine -am
mvn -Pnative package -DskipTests -pl emcip-conversation-context -am
mvn -Pnative package -DskipTests -pl emcip-llm-orchestrator -am

# The binary is at target/<module-name>
./emcip-policy-engine/target/emcip-policy-engine
----

=== Running Spotless with GraalVM Installed

`spotless-maven-plugin` is incompatible with JDK 25 (GraalVM CE).
Always run Spotless with the system JDK 21:

[source,bash]
----
# Temporarily unset GraalVM overrides
unset JAVA_HOME
# Or explicitly point at JDK 21
export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64

mvn spotless:apply
----

=== Architecture Notes

* Each native-enabled service has a `RuntimeHintsRegistrar` that scans all `org/hibernate/**/*.class` at AOT time to register full reflection access (required for Hibernate 7 strategy and logger classes).
* The `hibernate-graalvm` dependency provides `GraalVMStaticFeature`, which is activated via `--features=org.hibernate.graalvm.internal.GraalVMStaticFeature` in the native Maven profile.
* R2DBC-based services are excluded from native image support; see ADR-0007 for the rationale.

=== Docker Native Image Build

Each native-enabled service has a `Dockerfile.native` in its module directory.
The build must be invoked from the repo root (Docker build context).
All `Dockerfile.native` files use `ghcr.io/graalvm/native-image-community:25` as the builder — this must match the GraalVM version used locally, because Spring Boot 4 AOT records the JDK version at compile time and refuses to start on a lower runtime.

[source,bash]
----
docker build -f emcip-policy-engine/Dockerfile.native -t emcip-policy-engine:native .
docker build -f emcip-conversation-context/Dockerfile.native -t emcip-conversation-context:native .
docker build -f emcip-llm-orchestrator/Dockerfile.native -t emcip-llm-orchestrator:native .
----

Each build takes ~20 minutes and requires ~4 GB RAM. Results are cached by Docker layer.

=== Running with Docker Compose (native images)

A `docker-compose.native.yml` override file switches the three native-capable services
to use the pre-built images instead of the JVM `Dockerfile`:

[source,bash]
----
# Infrastructure + native services (full profile)
docker compose -f docker-compose.yml -f docker-compose.native.yml --profile full up

# Include llm-orchestrator
docker compose -f docker-compose.yml -f docker-compose.native.yml --profile full --profile llm up
----

NOTE: The Kafka health indicator takes 10–15 seconds to stabilise after startup.
The `/actuator/health` endpoint will return `DOWN` briefly — this is normal.

=== Pre-commit Checklist

[source,bash]
----
mvn spotless:apply          # Format code
mvn verify                  # Unit + integration + frontend tests pass (needs Docker)
mvn spotless:check          # Verify formatting (CI will check this)
----

CI runs `mvn -B verify` on every PR. A Spotless violation, PMD violation, or any failing unit, integration, or vitest test blocks merge.

== Image Publishing

Docker images are published to `ghcr.io/theyellow/ecip` automatically by GitHub Actions.

*Workflow file:* `.github/workflows/build-images.yml`

*Triggers:* push to `main` branch, or push of a tag matching `v*.*.*`.

*Tag convention:*

* Push to `main` → `staging` variants (e.g. `:staging`, `:jvm-staging`, `:native-amd64-staging`)
* Push of a `v*.*.*` tag → `latest` variants + semver (e.g. `:latest`, `:jvm-latest`, `:native-amd64`, `:v1.2.3`)

*Jobs:*

[cols="2,3,2,2"]
|===
|Job |Services |Tag on `main` push |Tag on version tag push

|`build-jvm-only`
|`intent-classifier`, `moderation-service`, `audit-service`, `admin-api`, `admin-ui`, `tdlib-adapter`
|`:staging`
|`:latest`, `:v1.2.3`

|`build-jvm-latest`
|`policy-engine`, `conversation-context`, `llm-orchestrator`
|`:jvm-staging`
|`:jvm-latest`, `:v1.2.3`

|`build-native-amd64`
|`policy-engine`, `conversation-context`, `llm-orchestrator`
|`:native-amd64-staging`
|`:native-amd64`, `:v1.2.3`
|===

After images are pushed, restart the cluster pods to pick them up — see
<<image-rollout,Rolling Out New Images>> in the Operations Guide, or the quick
reference at `docs/operations/rollout.md`.

NOTE: `emcip-tdlib-adapter` is a StatefulSet and must be restarted separately
with `rollout restart statefulset/emcip-tdlib-adapter`. It is skipped by
`rollout restart deployment`.

To build and push images locally with a registry prefix (for testing):

[source,bash]
----
# Requires docker login ghcr.io first
scripts/build-images.sh --jvm --registry ghcr.io/theyellow/ecip
scripts/build-images.sh --native amd64 --registry ghcr.io/theyellow/ecip
----

See `scripts/build-images.sh --help` for full options.

== Local Observability

=== Distributed Tracing in Local Dev

When Tempo is running (`docker compose up -d tempo`), all services export traces to
`http://ecip-tempo:4318`. Open http://localhost:14007 → Explore → Tempo to browse spans.

Trace IDs appear in application logs as `"traceId":"<32-hex-chars>"`. Use the Loki derived
field to jump from a log line directly to its trace.

If Tempo is *not* running, OTLP export fails silently — services start and function normally.
There is no fallback: traces are simply not stored.
