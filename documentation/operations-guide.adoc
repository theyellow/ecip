=== Kubernetes (Production)

Production deployments run on microk8s via Helm.
Images are built and published automatically by GitHub Actions on every push to `main`.
The operator does not build images manually for production.
See <<kubernetes-deployment>> for full setup instructions.

=== Docker Compose (Local Development / Quick Patch)

Docker Compose is the recommended local development and quick-patch environment.
Use it when developing features, debugging locally, or testing configuration changes before rolling to Kubernetes.
See the _Docker Compose Guide_ (`documentation/docker-compose-guide.adoc`) for setup instructions.

* Push to `main` → `staging` / `jvm-staging` / `native-amd64-staging` (updated on every merge)

Secrets are never stored in the chart. Create them manually once:

kubectl create secret generic emcip-secrets \

=== Topology-Dependent Configuration

Most configuration is safe to leave at its default. One setting is not, because it encodes the *shape of the proxy chain* rather than a preference, and nothing in the build can detect that it has become wrong:

[cols="1,1,3"]
|===
|Property |Default |Meaning

|`emcip.security.trusted-proxy-hops`
|`2`
|Which `X-Forwarded-For` entry admin-api trusts as the real client IP, counted *from the right*. Describes the chain `client → nginx ingress → admin-ui BFF → admin-api`.
|===

This value keys the `auth` rate limiter and the client IP recorded in login audit events. Set it too high and a caller can spoof their way into a fresh rate-limit bucket per request by prepending header entries; set it too low and admin-api keys on a proxy's own address, collapsing every client into one bucket.

WARNING: Changing the ingress, adding a CDN or load balancer in front of it, or altering how the admin-ui BFF forwards headers all invalidate this number — and every unit test still passes with a wrong value. Re-run the verification procedure in `docs/operations/rate-limiting.md` after any such change, and watch the `emcip.ratelimit.untrusted_ip` metric, which rises when the header is shorter than the hop count and resolution falls back to the socket address.

The nginx ingress `use-forwarded-headers` setting interacts with this directly: it determines whether nginx appends to an existing `X-Forwarded-For` or replaces it, which changes how many entries admin-api sees. The BFF appends its own hop in either mode, which is what makes hop 2 the client under both.

See `docs/operations/rate-limiting.md` for the limits themselves, the metrics to alert on, and the re-verification procedure.

[[image-rollout]]
=== Rolling Out New Images

After CI builds and pushes new images to `ghcr.io/theyellow/ecip` (on every
merge to `main`), restart the pods to pick them up. All images use
`pullPolicy: Always`.

[IMPORTANT]
====
`emcip-tdlib-adapter` is a **StatefulSet**, not a Deployment. It is skipped by
`rollout restart deployment -n emcip`. Always restart it explicitly.

Infrastructure pods (`emcip-postgres`, `emcip-emcip` Kafka, `emcip-entity-operator`,
Grafana, Loki, Prometheus) run upstream images — never restart them as part of an
application rollout.
====

[source,bash]
----
# Restart all application Deployments
microk8s.kubectl rollout restart deployment \
  emcip-admin-api emcip-admin-ui emcip-audit-service \
  emcip-intent-classifier emcip-moderation-service \
  emcip-conversation-context emcip-llm-orchestrator \
  emcip-policy-engine emcip-knowledge-engine \
  -n emcip

# Restart tdlib-adapter StatefulSet separately
microk8s.kubectl rollout restart statefulset/emcip-tdlib-adapter -n emcip

# Watch progress
microk8s.kubectl get pods -n emcip -w
----

To trigger a full rebuild without a code change: GitHub → Actions →
"Build and Push Docker Images" → Run workflow → `force_rebuild_all: true`.

For the full pod inventory and Liquibase troubleshooting, see
`docs/operations/rollout.md`.

== Service Data Isolation

Each microservice owns its own database tables. No service reads or writes another service's tables — not in local Docker Compose and not in Kubernetes.

[cols="1,3"]
|===
|Pattern |When to use

|Kafka topic
|Pipeline events: fire-and-forget, at-least-once, replayable. Use for all data that flows downstream (classified messages, moderation flags, audit events, etc.).

|REST via admin-api
|Management operations: synchronous queries from operators or the Admin UI. `emcip-admin-api` holds typed `WebClient` proxy clients for each domain service and authenticates with `X-Service-Token`. All downstream calls are protected by Resilience4j retry (3 attempts, exponential backoff) and circuit breaker. Read endpoints fall back to empty responses when a service is down; write endpoints propagate errors.
|===

If you are debugging a data discrepancy, always query the *owning service's* tables — never join across service boundaries in a single query. If you need cross-service data in a report, fetch each service's API individually.

==== Retry Configuration

Configured in `CommonKafkaConfig` (emcip-core):

* *Retries:* 3 attempts with exponential backoff (500ms, 1s, 2s).
* *Retryable exceptions:* `RetryableException`, `TransientDataAccessException`, network errors.

=== Audit Chain Integrity

`emcip-audit-service` maintains a tamper-evident hash chain over `audit_events`. `AuditChainVerificationJob` runs on `0 17 3 * * *` and logs at `INFO` when the chain verifies clean. A log line starting `CRITICAL: Audit chain integrity violation` means verification failed, and the `reason` field tells you which of two things happened:

* `CONTENT_TAMPERED` — a row's stored `integrity_hash` no longer matches the hash recomputed from that row's own content and `prev_hash`. Something changed the row's data in place (e.g. a superuser `UPDATE` bypassing the application).
* `BROKEN_LINKAGE` — a row's `prev_hash` no longer matches its predecessor's `integrity_hash`. A row was deleted or reordered outside the sanctioned purge path.

Either CRITICAL log is a genuine incident and should be investigated immediately (correlate with `brokenAtId`, `expectedHash`, `actualHash` in the log). Pre-activation rows (`integrity_hash IS NULL`) are skipped by design and are not evidence of tampering.

Manual `DELETE` statements against `audit_events` are blocked by a database trigger (`audit_no_delete`) — this is intentional, not a bug. The only sanctioned deletion path is the retention job (`AuditService.deleteRecordsOlderThan`), which sets `SET LOCAL emcip.audit_purge = 'on'` inside its own transaction before deleting; the flag is transaction-scoped and does not persist. If an operator genuinely needs to remove rows outside retention, do not attempt to disable or work around the trigger — escalate, since any such deletion invalidates the hash chain for every later row.

NOTE: **Retention boundary is a legitimate `BROKEN_LINKAGE` source.** After a retention purge, the oldest surviving row's `prev_hash` still points at a now-deleted row's `integrity_hash`. If a `verifyChain` window straddles that purge boundary (i.e. it includes the new oldest row), it will legitimately report `BROKEN_LINKAGE` for that row — this is expected at the retention boundary, not tampering. Correlate the `CRITICAL` log's `brokenAtId` against recent `AuditRetentionJob` purge runs before escalating.

|Set to `true` to activate knowledge enrichment. When `false`, no requests are made to the knowledge engine.

|`KNOWLEDGE_ENGINE_URL`
|`http://localhost:9088`
|Base URL of `emcip-knowledge-engine`. In Kubernetes, use the internal service URL (e.g., `http://emcip-knowledge-engine:9088`).

|`KNOWLEDGE_RELEVANCE_THRESHOLD`
|`0.70`
|Minimum cosine similarity score (0.0–1.0) for a knowledge passage to be included. Passages below this score are discarded. Raise to include only highly relevant results; lower to cast a wider net.

|`KNOWLEDGE_MAX_RESULTS`
|`5`
|Maximum number of passages to retrieve from the knowledge engine per LLM call.

|`KNOWLEDGE_CONTEXT_MAX_CHARS`
|`2000`
|Maximum total character length of the injected knowledge context block. The context is hard-truncated at this limit to avoid exceeding model token budgets.
|===

==== Enabling in Kubernetes

    KNOWLEDGE_ENRICHMENT_ENABLED: "true"

==== Behaviour When Knowledge Engine Is Unavailable

If the knowledge engine is unreachable (network error, pod not ready, wrong URL), enrichment silently degrades — the LLM call proceeds with the original unmodified user content. No error is returned to the caller. A `WARN` log line is emitted:

----
Knowledge engine unreachable — skipping enrichment: <error message>
----

Monitor for this log line (Loki query: `{app="emcip-llm-orchestrator"} |= "skipping enrichment"`) to detect misconfiguration.

=== Document Ingestion (SSRF Protection)

`emcip-knowledge-engine` fetches operator-submitted URLs during document ingestion. To prevent
server-side request forgery, the ingestion HTTP client resolves the target host and rejects any
address that falls in a hardcoded deny set: loopback, RFC-1918 private ranges, link-local
addresses (including the `169.254.169.254` cloud-metadata IP), the RFC-6598 carrier-grade NAT
range `100.64.0.0/10` (including Alibaba Cloud's `100.100.100.200` metadata IP), IPv6 unique-local
addresses, the wildcard address, and multicast/reserved ranges — unwrapping IPv4-mapped IPv6
addresses first. The
deny set is checked against the actually-resolved IP (not just the hostname), so it also closes
DNS-rebinding: redirects are disabled, and a blocked URL makes the ingestion job end `FAILED`
rather than returning any internal response content. This covers URL ingestion (submission and
reprocessing); it does not cover the separate connector fetchers.

==== Configuration

[cols="2,1,3"]
|===
|Key |Default |Description

|`emcip.ingestion.ssrf.allowed-hosts`
|_(empty)_
|List of hostnames or CIDRs that bypass the private-range block, for legitimate internal targets (e.g. an internal wiki). Default is empty, i.e. strict deny-private. The deny-set blocklist always applies to every other host.
|===

[source,yaml]
----
emcip:
  ingestion:
    ssrf:
      allowed-hosts:
        - wiki.internal.example.com
        - 10.20.0.0/24
----

Prefer CIDR entries over hostname entries where possible: a hostname allow-list entry permits
*any* IP that hostname currently resolves to (including private or metadata addresses), which a
DNS-rebinding attack or a compromised host could abuse, whereas a CIDR entry constrains the
bypass to a specific, fixed address range.

=== Admin UI Security Headers

`emcip-admin-ui` runs a `permitAll` Spring Security filter chain whose only job is to write
security response headers onto every response — it authenticates nothing (JWT auth lives at
`emcip-admin-api`). The chain enforces:

[cols="2,3"]
|===
|Header |Value

|`Content-Security-Policy`
|`default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'`

|`Strict-Transport-Security`
|`max-age=31536000 ; includeSubDomains` — max-age = 1 year (31536000s), includeSubDomains, no preload. The space before *and* after the `;` is not a typo: Spring Security's `HstsHeaderWriter` emits that literal.

|`X-Frame-Options`
|`DENY`

|`X-Content-Type-Options`
|`nosniff`

|`Referrer-Policy`
|`no-referrer`

|`Permissions-Policy`
|`geolocation=(), camera=(), microphone=(), payment=()`
|===

`style-src` currently allows `'unsafe-inline'` because the React frontend still uses inline
`style={{}}` attributes; `script-src` stays strict `'self'` with no such concession. Follow-up
RT2-007-F1 tracks migrating the frontend off inline styles so `style-src` can be tightened to
strict `'self'`.

CSP is emitted as a response header only — there is no `<meta http-equiv="Content-Security-Policy">`
in `index.html`.

`Strict-Transport-Security` requires the application to know the original request was HTTPS. TLS
terminates at the ingress, not at the `admin-ui` pod, so Spring must trust the ingress's
`X-Forwarded-Proto` header. This is enabled via `server.forward-headers-strategy: framework` in
`emcip-admin-ui`'s `application.yml` — without it, HSTS would never be written because Spring would
see every request as plain HTTP.

=== Moderation Rules

Rules are evaluated by `emcip-moderation-service` against every `policies.decisions` event.

==== Rule Types

[cols="1,3,2"]
|===
|Type |Behaviour |Example pattern

|`KEYWORD`
|Exact case-insensitive word match in message text
|`spam`

|`REGEX`
|Full Java `Pattern.compile()` regex applied to message text
|`\b(buy\|sell\|crypto)\b`

|`LENGTH`
|Fires when message character count exceeds the numeric pattern value
|`500`
|===

==== Configuring Rules via Admin API

[source,bash]
----
# Create a keyword rule
curl -X POST http://localhost:9087/api/admin/moderation-rules \
  -H "Authorization: Bearer <token>" \
  -H "Content-Type: application/json" \
  -d '{
    "ruleType": "KEYWORD",
    "pattern": "scam",
    "action": "FLAG",
    "enabled": true
  }'

# List all rules
curl http://localhost:9087/api/admin/moderation-rules \
  -H "Authorization: Bearer <token>"

# Delete a rule
curl -X DELETE http://localhost:9087/api/admin/moderation-rules/<id> \
  -H "Authorization: Bearer <token>"
----

In Kubernetes, replace `localhost:9087` with `http://emcip.local/api`.

==== Cache Refresh

The moderation-service caches active rules with a 5-minute TTL. Changes made via the Admin API take effect within 5 minutes without a service restart.

=== Troubleshooting

[cols="2,2,3"]
|===
|Symptom |Diagnosis command |Fix

|Pod stuck in `Pending`
|`kubectl describe pod <pod> -n emcip`
|Check `Events` section — usually a missing secret, PVC not bound, or node selector mismatch.

|Pod stuck in `CrashLoopBackOff`
|`kubectl logs <pod> -n emcip --previous`
|Read the previous container's last logs. Common: missing env var, wrong secret key, Kafka not ready.

|Kafka `Connection refused` (K8s)
|`kubectl get pods -n strimzi-system`
|Strimzi operator or Kafka CR may not be ready. Check `kubectl get kafka -n emcip`.

|PostgreSQL not ready (K8s)
|`kubectl logs <postgres-pod> -n emcip`
|Wait for Liquibase migration to complete. First start with NFS PVC may take 60s.

|Liquibase migration fails (K8s)
|`kubectl logs <service-pod> -n emcip \| grep Liquibase`
|A changeset is locked. Connect via `kubectl exec` to postgres pod and delete the lock row.

|TDLib auth fails (K8s)
|`kubectl logs -l app=emcip-tdlib-adapter -n emcip`
|Verify `telegram-*` keys in `emcip-secrets`. Interactive auth may be required via `kubectl exec`.

|Grafana shows no data (K8s)
|`kubectl logs -l app=emcip-loki -n emcip`
|Loki may not be ready. Check PVC is bound: `kubectl get pvc -n emcip`.

|===

== Backup & Restore

=== Creating a Backup

==== Kubernetes

[source,bash]
----
# Get the postgres pod name
PGPOD=$(kubectl get pod -l app=emcip-postgres -n emcip -o jsonpath='{.items[0].metadata.name}')

# Run pg_dump inside the pod and copy the dump locally
kubectl exec "$PGPOD" -n emcip -- \
  pg_dump -U emcip -Fc emcip > backup_$(date +%Y%m%d_%H%M%S).dump
----

For Docker Compose backup and restore, see the _Docker Compose Guide_.

=== Restore Procedure

[source,bash]
----
# Step 1: Scale down application services
kubectl scale deployment -l app.kubernetes.io/instance=emcip -n emcip --replicas=0

# Step 2: Copy dump file into postgres pod
PGPOD=$(kubectl get pod -l app=emcip-postgres -n emcip -o jsonpath='{.items[0].metadata.name}')
kubectl cp backup_20260422_120000.dump emcip/"$PGPOD":/tmp/backup.dump

# Step 3: Restore
kubectl exec "$PGPOD" -n emcip -- \
  pg_restore -U emcip -d emcip --clean /tmp/backup.dump

# Step 4: Restart services
kubectl scale deployment -l app.kubernetes.io/instance=emcip -n emcip --replicas=1
----

For Docker Compose restore, see the _Docker Compose Guide_.
