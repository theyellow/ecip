== 1. Architecture Overview

The ECIP platform connects to Telegram as a real user (not a bot), listens in various groups, channels, and discussion chats, collects information passively, and can later interact with other users. This approach enables deep integration and context awareness, going beyond the limitations of the Telegram Bot API.

== 2. Component & Service Breakdown

=== 2.1 Component Responsibilities

- TDLib Adapter: Connects to Telegram as a real user via TDLib, listens in groups/channels/discussion chats, normalizes updates, publishes events to Kafka. Enables both passive information collection and later active interaction with other users.
- Conversation Context Service: Tracks threads, speaker roles, enriches context for all observed conversations in Telegram groups/channels/discussions.
- Intent Classifier: Rule-based classification of message intent for all collected Telegram messages.
- Policy Engine: Deterministic policy logic, escalation, versioning for all actions and responses.
- LLM Orchestrator: Model routing, prompt templates, cost control for AI-based responses and analysis.
- Moderation Service: Toxicity filter, rule violation detection for all collected and generated content.
- Audit/Observability Service: Logging, tracing, metrics, cost tracking for all events and actions.
- Admin API: Admin endpoints, JWT security, service-to-service authentication, configuration of Telegram user credentials and group/channel selection.
- Kafka: Event backbone for all services, transports all Telegram events and internal actions.
- PostgreSQL: Persistent storage for all services, including collected Telegram data and context.

== 4. Technology Stack & Guardrails

=== 4.1 Stack Overview

- Java 25, Spring Boot 4: Modern, robust, reactive microservices
- Kafka: Event-driven backbone, decoupling, scalability
- PostgreSQL: Reliable, transactional persistence
- TDLib: Full Telegram client integration as a real user (not just Bot API)
- OpenTelemetry, Prometheus: Observability, metrics, tracing
- Vault: Secret management
- JWT: API and service-to-service security
- Maven: Build, dependency management

=== 4.2 Guardrails

- All event-driven, no direct service-to-service calls (except Admin API)
- All external communication with Telegram via TDLib as a real user (not Bot API)
- All responses must pass through policy and moderation logic
- No business logic in integration/adapter layers
- All configuration and secrets via Vault
- All code and infrastructure changes require ADR (see /docs/adr/)
- All technical decisions must be documented (ADR or architecture.adoc)
- No direct DB access from outside services (only via service APIs)
- Observability (logging, tracing, metrics) is mandatory for all services
