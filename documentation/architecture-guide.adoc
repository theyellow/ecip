== Introduction

EMCIP (Enterprise Messenger Community Intelligence Platform) connects to Telegram as a *real user* (not a bot) via TDLib, listens passively in groups, channels, and discussion chats, classifies message intent, evaluates community policy rules, and optionally generates LLM responses or applies moderation actions.

=== Operating Modes

[cols="1,3"]
|===
|Mode |Description

|*React*
|Policy rule evaluates intent and produces a structured response via the LLM Orchestrator.

|*Summarize*
|Conversation context is periodically summarised and stored for retrieval.

|*Moderate*
|The Moderation Service applies keyword, regex, or length rules and flags violations.

|*Observe*
|All pipeline events are written to the Audit Service — read-only observation with no actions.
|===

NOTE: Production runtime is Kubernetes (microk8s) via Helm.
Local development uses Docker Compose. See the _Operations Guide_ for deployment details.

NOTE: For setup steps and development prerequisites, see the _Developer Guide_.

=== LLM Orchestrator

[plantuml,c3-llm,png]
----
include::diagrams/c3-llm-orchestrator.puml[]
----

The LLM Orchestrator (`emcip-llm-orchestrator`) generates AI responses for `RESPOND` policy decisions. `PolicyDecisionConsumer` listens on `policies.decisions` and delegates to `LlmCallService`, which: selects a `ModelConfig` for the task type, renders a `PromptTemplate` with message variables, optionally enriches the user content with knowledge context (see below), reads the active `LlmProviderConfig` (base URL + optional API key) from the database, and calls `OpenAiCompatibleLlmClient` which POSTs to `{baseUrl}/v1/chat/completions`. Cost is logged via `CostTrackingService` after each successful call.

The LLM provider URL is not an environment variable — it is stored in the `llm_provider_configs` table and managed at runtime via Admin UI → AI Config → LLM Provider. The `OrchestratorController` exposes REST endpoints for provider-config CRUD, a connectivity test (`GET /v1/models`), model config management, prompt template management, and cost queries.

*Knowledge enrichment (Epic 26.10):* Before each LLM call, `LlmCallService` can optionally prepend relevant knowledge-base passages to the user prompt. When enabled, `KnowledgeContextEnricherService` calls `KnowledgeEngineClient` which POSTs to `emcip-knowledge-engine`'s `POST /api/knowledge/search` (HYBRID mode). Results are filtered by a configurable relevance threshold; passages above the threshold are formatted as `[Source: <ref>]\n<content>` blocks and prepended to the user message with a `---` separator. If the knowledge engine is unreachable, enrichment silently degrades and the LLM call proceeds with the original content. Enrichment is off by default and enabled per-deployment via environment variables (see Operations Guide → Knowledge Enrichment Configuration).

=== Knowledge Engine

[plantuml,c3-knowledge-engine,png]
----
include::diagrams/c3-knowledge-engine.puml[]
----

The Knowledge Engine (`emcip-knowledge-engine`) provides ontology-driven knowledge management with two knowledge layers: *Community Knowledge* (extracted from Telegram chat messages) and *Factual Knowledge* (ingested from external documents via URL or file upload). `KnowledgeMessageConsumer` listens on `knowledge.raw.messages` and delegates to `KnowledgeExtractionService`, which: stores raw content as a `KnowledgeDocument` with a vector embedding (via pgvector) for immediate semantic search, then calls `emcip-llm-orchestrator` for entity/relationship extraction using ontology-driven prompts. Extracted entities are deduplicated via `EntityResolutionService` (exact match → alias table → embedding similarity) and stored as `GraphNode`/`GraphEdge` entries in the Apache AGE graph layer.

The ontology (concept types, relationship types, and their properties) is a first-class configuration artifact stored in the database and managed via REST endpoints. New entity types or relationships are added by extending the ontology — no schema migrations or code changes required. The initial seed ontology defines Person, Topic, Message, Source, and Document concept types with DISCUSSES, AUTHORED, MENTIONS, CITES, and RELATED_TO relationships.

Query capabilities include vector-based semantic search (pgvector cosine similarity), graph traversal (Apache AGE / openCypher), and hybrid search combining both. The service exposes REST endpoints for search, ontology management, document ingestion, and bulk backfill. Service-to-service enrichment uses the `knowledge.events` Kafka topic.

*Enrichment connector pipeline (Epic 42):* `EnrichmentScheduler` runs every minute (cron `17 * * * * *`) and evaluates each enabled `EnrichmentSource` against its per-source schedule using `CronExpression.parse()`. When triggered — either by schedule, by `ENTITY_CREATED` events on `knowledge.events` (via `EntityEnrichmentConsumer`, group `knowledge-engine-entity-enrichment`), or by manual API trigger (via `ManualEnrichmentConsumer`, group `knowledge-engine`, topic `knowledge.enrichment.trigger`) — `EnrichmentPipelineService` executes a 6-stage pipeline: (1) resolve connector, (2) resolve API key (tenant-override → global fallback), (3) fetch from external API, (4) deduplicate by `sourceRef+sourceType`, (5) store as `KnowledgeDocument` with best-effort embedding, (6) finalize `EnrichmentRun` with SUCCESS/PARTIAL/FAILURE status. Vendor API keys are stored in `ke_vendor_api_keys`, encrypted at rest (AES-256-GCM) and masked in the UI; enrichment sources in `ke_enrichment_sources`; run history in `ke_enrichment_runs`.

Repository interfaces (`GraphRepository`, `VectorSearchRepository`) provide an abstraction layer so the underlying storage can be swapped to dedicated graph or vector databases (e.g., Neo4j, Qdrant) without changing business logic.

=== Admin API

[plantuml,c3-admin-api,png]
----
include::diagrams/c3-admin-api.puml[]
----

The Admin API (`emcip-admin-api`) is the single management entry point for operators and the Admin UI. It uses Spring WebFlux with two filter chains: `JwtAuthenticationFilter` for human operators and `ServiceTokenAuthenticationFilter` for internal service calls. Controllers (`AuthController`, `TenantController`, `PolicyRuleController`, `AuditController`, and others) share `TenantWebFilter` which binds the `X-Tenant-Id` header to the Reactor subscriber context.

Domain data (moderation rules, audit events, policy decisions) is accessed via REST proxy clients (`ModerationServiceClient`, `PolicyEngineClient`, `AuditServiceClient`) that call each domain service's own REST API with an `X-Service-Token` header. The admin-api does not share or directly access the database tables of other services.

All downstream REST calls are protected by a three-layer Resilience4j stack: *retry* (3 attempts with exponential backoff: 500ms → 1s → 2s), then *circuit breaker* (sliding window of 10 calls, 50% failure threshold, 30s open state), then *fallback* on read operations. When a downstream service is temporarily unavailable, list endpoints (`listEvents`, `listRules`, `listDecisions`) return empty responses so the UI stays navigable. Write operations propagate errors as 503 so operators know their action did not succeed.

The admin-api also provides an *AI Research chat* — a multi-turn conversation endpoint (`POST /api/flags/{id}/chat`) that prepends the flag context as a system prompt and forwards the messages array to the LLM Orchestrator's `POST /api/chat` endpoint. This lets operators interactively investigate flagged messages with LLM assistance before deciding on a response.

The admin-api exposes *LLM cost analytics* via `CostsProxyController` — three read-only endpoints (`/api/costs/totals`, `/api/costs/by-model`, `/api/costs/by-day`) that proxy to the LLM Orchestrator's cost aggregation queries. The `COSTS_READ` permission is granted to both ADMIN and TENANT_ADMIN roles, giving operators visibility into LLM usage and spend.

The admin-api also supports *operator actions* — currently, operators can reply to flagged messages directly from the Flag Detail modal. The reply flow resolves the Telegram account watching the flagged chat (via `GroupProfile` → `AccountWatchedGroup` → `TelegramAccount`), sends the message through `emcip-tdlib-adapter`'s `POST /internal/send-message/{accountId}` endpoint (with Resilience4j circuit breaker + retry), and publishes an `OPERATOR_REPLY` audit event to the `audit.events` Kafka topic.

`FlagService.reply()` supports a `NOTE` target for internal operator notes. When the reply `target` equals `"NOTE"`, the service skips TDLib send entirely and publishes an `OPERATOR_NOTE` audit event to the `audit.events` Kafka topic with the note text in the event details. The response returns `messageId: 0`, `target: "NOTE"`, and `markedActioned: false`. No Telegram account resolution is performed for notes.

== Event Architecture

The pipeline is fully event-driven. Core pipeline services communicate via Kafka topics — no synchronous HTTP calls between them. Management and configuration operations are exposed by each service as REST endpoints and accessed by `emcip-admin-api` via internal proxy clients (`ModerationServiceClient`, `PolicyEngineClient`, `AuditServiceClient`).

IMPORTANT: No service may access another service's database tables directly. Cross-service data access uses Kafka (pipeline events) or REST (management queries via admin-api). The `emcip-admin-api` module is the only "controller" in this sense — it aggregates management APIs but delegates storage to each domain service.

== Observability Architecture

=== Distributed Tracing

All 9 services use *Micrometer Tracing* with the OpenTelemetry bridge (`micrometer-tracing-bridge-otel`).
Traces are exported via OTLP/HTTP to *Grafana Tempo* on port 4318. Tempo stores spans with a 14-day
retention window.

W3C `traceparent` headers propagate trace context across HTTP calls and Kafka message headers,
enabling end-to-end trace correlation across service boundaries.

Trace IDs appear in structured JSON logs as the `traceId` field. Grafana's Loki datasource
is configured with a derived field that links any `traceId` value directly to the matching Tempo trace.

== Security Architecture

=== JWT Authentication Chain

The Admin API uses two parallel filter chains registered as Spring `WebFilter`:

. *`JwtAuthenticationFilter`* — validates `Authorization: Bearer <token>` header. Extracts `sub` (username) and `roles` claims. Populates `ReactiveSecurityContextHolder`.
. *`ServiceTokenAuthenticationFilter`* — validates `X-Service-Token` header for internal service calls.

Tokens are signed with `ADMIN_JWT_SECRET` (HS256). Expiry is configurable via `app.jwt.expiration`.

=== Tenant Isolation

Every entity table contains a `tenant_id UUID NOT NULL` column. Isolation is enforced at the data-access layer across two execution models:

*Servlet services* (policy-engine, moderation-service, conversation-context, llm-orchestrator): `TenantContextFilter` (`OncePerRequestFilter`) extracts the `X-Tenant-Id` HTTP header and stores it in `TenantContext` (ThreadLocal). `TenantFilterAspect` (Spring AOP `@Before` pointcut on `@Repository` beans) then enables the Hibernate named filter `tenantFilter` on the current session before every query. Hibernate automatically appends `AND tenant_id = :tenantId` to all annotated entity queries.

*Admin API* (reactive / WebFlux): `AdminTenantContextFilter` (`WebFilter`) either binds the tenant ID for normal tenant callers or activates admin mode for `ROLE_ADMIN` JWT holders. Repositories use scoped Spring Data R2DBC methods (e.g. `findByIdAndTenantId`) — Hibernate filters are not available in the reactive stack.

[plantuml,seq-tenant,png]
----
include::diagrams/sequence-tenant-propagation.puml[]
----

Kafka messages carry `tenant_id` as a record header. Producers call `TenantAwareKafkaSupport.addTenantHeader(record)` to copy the current `TenantContext` value into the record header. Consumers call `TenantAwareKafkaSupport.bindTenantFromRecord(record)` to restore it, and call `TenantContext.clear()` in a `finally` block after processing.

=== Secrets at Rest

Secret columns are encrypted with AES-256-GCM before storage: `telegram_accounts.session_string`, `telegram_accounts.api_hash`, `ke_vendor_api_keys.api_key`, and `llm_provider_configs.api_key`. The single `SecretCipher` (in `emcip-core`) stores values as `v1:` + base64 of `iv ‖ ciphertext ‖ tag`; the `v1:` prefix is a version marker enabling future key rotation without re-encrypting stored data. The key comes from the `EMCIP_SECRET_KEY` environment variable (base64, 32 bytes), sourced from a Kubernetes Secret and never sent to PostgreSQL. Only admin-api, knowledge-engine, and llm-orchestrator require it — each `@Import`s `SecretCipherConfig` and fails startup without a valid key.

JPA services (knowledge-engine, llm-orchestrator) apply encryption transparently via a per-column `EncryptedStringConverter` (`@Convert`); admin-api's reactive R2DBC path encrypts and decrypts explicitly in the service layer. Reads are *fail-closed*: a stored value lacking the `v1:` prefix throws rather than being used as plaintext, so a missed migration surfaces loudly and names the offending column. There is no automatic backfill — pre-existing rows are migrated once, by hand, per `docs/operations/secrets-encryption.md`.

=== Audit Integrity (Hash Chain)

`audit_events` rows form an append-only, tamper-evident hash chain: `AuditService.saveWithChain()` computes `integrity_hash = sha256(eventId|createdAt|eventType|actorId|resourceType|resourceId|prev_hash)`, folding each row's predecessor hash into its own digest so altering any earlier row cascades into every later `integrity_hash`. The genesis row (first post-activation write) has `prev_hash = null`; pre-activation rows keep a `NULL` `integrity_hash` and are skipped by verification.

The read-tail → compute → insert sequence is an unsynchronized read-modify-write, and the audit consumer runs with `setConcurrency(3)`, so it is serialized by a cluster-wide Postgres advisory lock (`pg_advisory_xact_lock`, a fixed key constant in `AuditService`) held for the duration of an R2DBC `TransactionalOperator` transaction — released automatically on commit/rollback, so it cannot leak even on failure. This makes the chain correct across concurrent listener threads and future replicas alike. `AuditChainVerificationJob` (cron `0 17 3 * * *`) recomputes the stored hash from each row's content and prior hash — detecting content tampering — and separately checks `newer.prev_hash == older.integrity_hash` — detecting deletion/reordering — reporting which via a `CONTENT_TAMPERED` / `BROKEN_LINKAGE` discriminator.

A DELETE-prevention trigger (`audit_no_delete`, migration `004`) fails closed on any `DELETE` against `audit_events` unless the transaction has `SET LOCAL emcip.audit_purge = 'on'`. `AuditService.deleteRecordsOlderThan()` (the retention job's purge path) sets this flag inside its own transaction before deleting, so the sanctioned purge still works while ad-hoc or manual deletes are rejected by the database itself.

The consumer (`AuditEventConsumer`) is a synchronous `@KafkaListener` (five listener methods, one per source topic) calling `saveWithChain()`, hardened by a `DefaultErrorHandler` (exponential backoff: 1s/2s/4s… capped at 30s, gives up after ~60s elapsed) that recovers exhausted or non-retryable failures to `<topic>.dlq` via `DeadLetterTopicHandler`; `JacksonException` (malformed payloads) is classified non-retryable and routed to the DLQ immediately. `AckMode.MANUAL_IMMEDIATE` means the offset commits only after a successful save or after the record durably lands on the DLQ — never a silent loss. Persistence stays fully reactive (`saveWithChain` returns a `Mono`, backed by R2DBC); a single `.block()` bridges at the Kafka consumer thread, which runs on a dedicated listener container thread pool, not a WebFlux event loop.

NOTE: An earlier design considered rewriting the consumer with `ReactiveKafkaConsumerTemplate` to remove the `.block()`. This was dropped: the class was removed from spring-kafka 4.x, and reactor-kafka (the library it wrapped) is discontinued. See `docs/superpowers/specs/2026-07-25-audit-integrity-redesign-design.md` ("Decision revision") for the full rationale.

== ADR-001: Technology Stack Selection

*Status:* Accepted (2026-04-15). *Amendment:* Java 25 production target added 2026-04-21.

*Decision:* Java 21, Spring Boot 4, Maven, Apache Kafka, PostgreSQL 16, R2DBC/JPA, Docker.

*Context:* EMCIP requires high-throughput event processing, reactive non-blocking I/O, strong typing, and cloud-native deployment. Java 21 virtual threads simplify concurrent programming compared to explicit reactive chains.

*Alternatives rejected:* Go (smaller ecosystem), Node.js (single-threaded, type safety), Python (GIL + performance), Kotlin (smaller talent pool at project start).

[appendix]
== ADR-002: Event-Driven Architecture with Kafka

*Status:* Accepted (2026-04-15).

*Decision:* All inter-service communication uses Kafka topics (JSON, 3 partitions each). No synchronous HTTP between pipeline services. At-least-once delivery with idempotent consumers.

*Context:* Multi-stage pipeline (ingest → classify → evaluate → respond → audit) requires backpressure handling, independent scaling, and replay capability. Ten topics defined (see §6 Kafka Topic Reference).

*Alternatives rejected:* RabbitMQ (no replay), Pulsar (smaller ecosystem), NATS (less durable), HTTP/gRPC (tight coupling).

[appendix]
== ADR-003: Data Persistence with PostgreSQL

*Status:* Accepted (2026-04-15). *Amendment:* Migrated from R2DBC to JPA during Phase 2.

*Decision:* PostgreSQL 16 as primary database. JPA/Hibernate (JDBC) for Phase 2/3 services with complex domain models. Liquibase for all schema migrations.

*Context:* Initial R2DBC approach was replaced because JPA provided better Spring Data integration, easier testing, and simpler transaction management for services with entity associations.

[appendix]
== ADR-004: R2DBC and Reactive Stack for Phase 4 Services

*Status:* Accepted (2026-04-21).

*Decision:* R2DBC with Spring Data R2DBC is approved for `emcip-moderation-service`, `emcip-audit-service`, and `emcip-admin-api`. These three services have flat schemas, high I/O throughput, and a fully reactive WebFlux runtime — the profile where R2DBC outperforms JPA.

*Relationship to ADR-003:* ADR-003 remains authoritative for Phase 2/3 services. ADR-004 extends it for Phase 4 services only. The rule is: JPA for complex domain models; R2DBC for flat schemas + WebFlux.

*Consequence:* All R2DBC services include `spring-boot-starter-jdbc` as `runtime` scope for Liquibase only.

== ADR-008: Knowledge Management with PostgreSQL Extensions

*Status:* Accepted (2026-06-13).

*Decision:* Use pgvector (vector similarity search) and Apache AGE (graph database with openCypher) as PostgreSQL extensions instead of dedicated database engines (Neo4j, Qdrant). Business logic accesses capabilities through abstraction interfaces (`GraphRepository`, `VectorSearchRepository`) to preserve migration path to dedicated engines.

*Context:* Knowledge management (#26, #27) requires graph and vector capabilities. Adding dedicated servers would increase operational overhead on the single-node microk8s cluster. PostgreSQL extensions provide both capabilities within the existing instance. Apache AGE uses the same openCypher query language as Neo4j, making future migration straightforward.

*Alternatives rejected:* Neo4j + Qdrant (ops overhead), Neo4j only (no vector search), Qdrant only (no graph traversal).
