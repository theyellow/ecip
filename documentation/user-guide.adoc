:toclevels: 3

This guide covers two audiences:

* *Part I — Admin UI*: Platform administrators using the browser-based interface at http://emcip.local/.
* *Part II — REST API*: Developers and automation scripts calling the Admin API directly at http://emcip.local/api.

NOTE: EMCIP runs on microk8s. The Admin UI is at `http://emcip.local/` and the Admin API at `http://emcip.local/api`.
For local Docker Compose development, substitute `http://localhost:14009` and `http://localhost:9087` respectively.
See the _Docker Compose Guide_ for local setup.

NOTE: For JWT internals and the full security architecture, see the _Architecture Guide_.

== Part I — Admin UI

=== Login

Open http://emcip.local/ in a browser.

----

Enter your username and password in the login form and click *Sign In*. The UI calls `POST /api/auth/token` and stores the returned JWT in a JavaScript variable.

[IMPORTANT]
====
The JWT is stored in memory (a JS variable), not in `localStorage`. If you reload the page, you will be logged out and must sign in again. This is intentional — it prevents token theft via XSS.

=== Tenant Management

A *tenant* is a logical boundary for data isolation. All policy rules, audit events, and moderation flags belong to exactly one tenant. This enables a single EMCIP installation to serve multiple independent communities.

==== Create a Tenant

. Navigate to *Tenants* in the sidebar.
. Click *New Tenant*.
. Enter the community name in the *Name* field.
. Click *Create*. The new tenant appears in the list with its UUID.

==== Delete a Tenant

[WARNING]
====
Deleting a tenant is irreversible. All policy rules, audit events, and moderation flags belonging to the tenant are permanently deleted via cascading database operations. There is no soft-delete or undo.
====

. Find the tenant in the list.
. Click the *Delete* button (trash icon).
. Confirm in the warning dialog.

==== Tenant IDs

The UUID shown in the tenant list is the `X-Tenant-Id` value required by all API calls scoped to that tenant.

=== Policy Rules

A *policy rule* maps an intent type to a moderation action. When the Policy Engine classifies a message as a given intent, it looks up the highest-priority active rule for that intent and applies the configured action.

==== Rule Actions

[cols="1,3"]
|===
|Action |Effect

|`ALLOW`
|No action taken. Message passes through.

|`WARN`
|Emits a `moderation.flags` event with severity WARN. No message action.

|`MUTE`
|Triggers a mute action on the sender (via TDLib Adapter).

|`BAN`
|Triggers a ban action on the sender (via TDLib Adapter).
|===

==== Creating a New Rule Version

Policy rules are versioned. Creating a new version automatically deactivates the previous version for the same rule name.

. Navigate to *Policy Rules*.
. Click *New Rule Version*.
. Fill in:
** *Name*: unique identifier for this rule (e.g., `spam-block`).
** *Action*: one of `ALLOW`, `WARN`, `MUTE`, `BAN`.
** *Priority*: lower numbers are evaluated first.
** *Effective From* (optional): activation date/time.
** *Effective To* (optional): expiry date/time for time-limited rules.
. Click *Save*. The previous version for this name is automatically deactivated.

==== Rule Version History

Click the *History* button (clock icon) next to any rule to open the version history modal. It shows all versions with their activation timestamps, deactivation timestamps, and actions.

=== Audit Log

The audit log is an append-only record of every significant event in the pipeline.

==== Event Types

[cols="1,3"]
|===
|Type |Description

|`MESSAGE_RECEIVED`
|A Telegram message was ingested by the TDLib Adapter.

|`POLICY_DECISION`
|The Policy Engine made a decision (includes ruleId and reasoning).

|`LLM_RESPONSE`
|The LLM Orchestrator generated a response (includes model and token counts).

|`MODERATION_FLAG`
|The Moderation Service flagged a message (includes rule type and pattern).
|===

==== Filtering Events

Use the filter bar at the top of the Audit Log view:

* *Event Type* — select one type or leave blank for all.
* *From* / *To* — date range picker.
* Click *Apply* to refresh results.

Results are paginated (50 per page). Use *Previous* / *Next* to navigate.

==== Inspecting Event Payload

Click any row to expand the event payload. The raw JSON is displayed with syntax highlighting for inspection.

=== Flags

The *Flags* page shows every message that triggered a non-ALLOW policy decision — it is the primary human-review surface for automated moderation actions.

NOTE: Only decisions where the Policy Engine applied an action (e.g., `FLAG`, `WARN`, `BAN`) appear here. `ALLOW` decisions are not shown.

==== Columns

[cols="1,3"]
|===
|Column |Description

|*Timestamp*
|When the policy decision was made.

|*Decision*
|The action the Policy Engine applied: `FLAG`, `WARN`, `MUTE`, `BAN`, `DELETE`, or `ESCALATE`.
Color-coded: blue = FLAG, yellow = WARN/MUTE, red = BAN/DELETE, gray = ESCALATE.

|*Intent*
|The intent the classifier assigned to the message (e.g., `SPAM`, `UNKNOWN`).

|*Confidence*
|Classifier confidence as a percentage (0 %–100 %).

|*Message*
|The original Telegram message text (truncated). Hover to see the full text.
Empty for decisions made before the metadata enrichment was deployed.

|*Reason*
|The rule reasoning string stored with the decision.

|*Status*
|Review state: `NEW` (blue), `REVIEWED` (gray), `ACTIONED` (green).
|===

==== Filtering

Use the two dropdowns in the top-right corner:

* *Decision* — filter to a specific action type, or leave as "All decisions".
* *Size* — number of rows to show: 25, 50, 100, or 200.

Results are always ordered newest-first.

==== Inspecting and Reviewing a Flag

Click any row to open the *Flag Detail* modal. The modal shows the full (untruncated) message text, metadata fields (Chat ID, Sender ID), the matched policy ID, event IDs, and the current review status.

To change the status, click one of the status buttons in the modal (*New*, *Reviewed*, or *Actioned*). The change is saved immediately via `PATCH /api/flags/\{id}/status` and reflected in both the modal and the table row. There is no undo in the UI (the API accepts any value).

Typical review workflow:

. Row arrives as *NEW* (blue).
. Operator clicks the row and reads the full message text in the modal.
. Operator clicks *Reviewed* — status changes to *REVIEWED* (gray).
. After taking action (e.g., banning the user manually), operator clicks *Actioned* — status changes to *ACTIONED* (green).

==== Understanding the Pipeline

Each row in Flags corresponds to one complete pipeline run:

. A Telegram message was received by the TDLib Adapter and published to `telegram.raw.messages`.
. The Intent Classifier consumed the message, classified it, and published to `messages.classified`.
. The Policy Engine evaluated the classification against active rules and, if a non-ALLOW rule matched, stored the decision in `policy_decisions` and published to `policies.decisions`.
. The Audit Service consumed all three events and stored them in `audit_events`.

The *Flags* page reads directly from `policy_decisions` (decisions where `decision != 'ALLOW'`).
The *Audit Log* page reads from `audit_events` (all pipeline steps, regardless of decision).

=== Moderation Rules

*Moderation Rules* define keyword- or pattern-based filters that the Moderation Service applies to every incoming message independently of the policy engine.

==== Rule Types

[cols="1,2,2"]
|===
|Type |Matches when |Pattern example

|`KEYWORD`
|Message contains the exact word (case-insensitive)
|`scam`

|`REGEX`
|Message matches a Java regex pattern
|`\b(buy\|sell\|crypto)\b`

|`LENGTH`
|Message character count exceeds the numeric value
|`500`
|===

==== Actions

`FLAG`, `WARN`, `MUTE`, `BAN`, `DELETE`, `ALLOW`. Matching rules emit a `MODERATION_FLAG` event which the Audit Service records.

==== Managing Rules

. Navigate to *Moderation Rules* in the sidebar.
. Click *New Rule* to open the create form.
. Fill in: *Type*, *Pattern*, *Action*, and optionally toggle *Enabled*.
. Click *Save*. The rule is active within 5 minutes (the Moderation Service polls the database on a short cache TTL).
. To delete a rule, click the trash icon in its row. Deletion is permanent.

NOTE: Rules can be toggled on/off using the *Enabled* switch in the list without deleting them.

=== Groups

The *Groups* page manages *group profiles* — the metadata EMCIP stores for each Telegram group it watches. A group profile is created automatically when you watch a group via the Telegram Accounts page, and can be edited here.

==== Group Profile Fields

[cols="1,3"]
|===
|Field |Description

|*Telegram Chat ID*
|The numeric Telegram chat ID (negative for supergroups). Set at creation, read-only afterwards.

|*Name*
|Human-readable label for the group.

|*Description*
|Optional internal notes.

|*Moderation Level*
|`LOW`, `MEDIUM`, `HIGH`, or `STRICT`. Referenced by policy rules for level-gated actions. Color-coded: green / blue / yellow / red.

|*Auto-respond*
|If enabled, the LLM Orchestrator sends automated replies for matched messages.

|*Welcome Message*
|Text the bot sends to new group members (if auto-respond is enabled).

|*Tenant*
|Assigns the group to a tenant for data isolation.
|===

==== Editing a Group Profile

. Navigate to *Groups* in the sidebar.
. Click the pencil icon on a group row.
. Edit the fields and click *Save*.

NOTE: The Telegram Chat ID cannot be changed after creation. Remove and re-add the group if you need to correct it.

=== Simulate

The *Simulate* page publishes a synthetic Telegram message event directly into the processing pipeline. Use it to test rules and verify end-to-end behaviour without sending a real message.

==== How to Use

. Navigate to *Simulate* in the sidebar.
. Fill in:
** *Chat ID* — the numeric Telegram chat ID of a watched group (negative integer).
** *Sender ID* — any string identifying the simulated sender (default: `sim-user`).
** *Sender Type* — `USER` or `BOT`.
** *Message Text* — the content to classify.
. Click *Publish*. The event is injected into `telegram.raw.messages`.
. Within a few seconds the message flows through Intent Classifier → Policy Engine → Audit Service.
. Check the *Flags* page (for non-ALLOW decisions) and the *Audit Log* to confirm the pipeline ran.

NOTE: Simulated messages are indistinguishable from real messages in the pipeline.
They will appear in the Audit Log and may trigger policy actions.

=== AI Config

The *AI Config* page manages the model registry used by the LLM Orchestrator. Each entry maps a *model key* to a specific provider and model name, along with cost and performance metadata.

==== Fields

[cols="1,3"]
|===
|Field |Description

|*Model Key*
|Internal identifier used in prompt templates (e.g., `claude-default`).

|*Provider*
|LLM provider: `anthropic`, `openai`, `google`, etc.

|*Model Name*
|Exact model identifier sent to the provider API (e.g., `claude-sonnet-4-6`).

|*Task Type*
|`GENERAL`, `CLASSIFICATION`, `SUMMARIZATION`, etc. Used for routing.

|*Priority*
|Lower number = preferred when multiple models match a task type.

|*Active*
|Inactive models are excluded from routing.
|===

==== Managing Models

. Navigate to *AI Config* in the sidebar.
. Click *Add Model* to open the create form.
. Fill in the required fields (*Model Key*, *Provider*, *Model Name*) and click *Save*.
. Edit an existing model with the pencil icon; delete with the trash icon.

=== Telegram Account Management

EMCIP connects to Telegram as a full user-bot client (not a bot API). Each Telegram account
authenticates interactively — the platform sends a code to the account's phone and requires
entry via the Admin UI.

==== Adding a Telegram Account

. Navigate to *Telegram* in the sidebar.
. Click *Add Account*.
. Enter the phone number in international format (e.g., `+491234567890`).
. Click *Send Code*. Telegram sends a verification code to the phone.
. Enter the received code in the *Verification Code* field.
. Click *Authenticate*. The account status changes to *ACTIVE* when the session is established.

NOTE: New accounts start in `UNCONFIGURED` status. The status progresses through `AWAITING_CODE`
(and optionally `AWAITING_PASSWORD` for 2FA-enabled accounts) before reaching `ACTIVE`.

NOTE: The verification code arrives as a Telegram message from the Telegram service itself.
Check the Telegram app on the registered phone to retrieve it.

[WARNING]
====
Each Telegram account can only be active in one session at a time. Re-authenticating an
account after session expiry requires removing and re-adding it.
====

==== Account Status Values

[cols="1,3"]
|===
|Status |Meaning

|`UNCONFIGURED`
|Account created; authentication not started.

|`AWAITING_CODE`
|Verification code sent to phone. Waiting for the operator to enter the code.

|`AWAITING_PASSWORD`
|Two-factor authentication (2FA) password required. Enter the cloud password.

|`ACTIVE`
|Session established. The account is receiving Telegram updates.

|`DISCONNECTED`
|Session terminated or authentication failed. Remove and re-add the account to retry.
|===

==== Watching Groups

Once an account is *ACTIVE*, you configure which Telegram groups it monitors.
EMCIP only publishes messages from *watched* groups to the processing pipeline —
unwatched groups are silently ignored.

==== Discovering Groups

. Find the account in the accounts table.
. Click *Groups*. An inline panel expands showing the account's watched groups.
. Click *Discover Groups*. The platform queries TDLib to list all groups the account
  is currently a member of.
. The discover modal shows: Name, Member Count, Type, and a *Watch* button per group.

NOTE: If the list appears empty, click *Refresh* in the modal header. TDLib may take a few
seconds to sync chats after a fresh session.

==== Watching a Group

In the Discover Groups modal, click *Watch* next to the group. The group moves to the watched
sub-table immediately. The *Watch* button is replaced by *Watching* (grayed out).

==== Unwatching a Group

In the watched groups sub-table, click *Unwatch*. Messages from that group stop reaching the
pipeline immediately.

==== Joining by Invite Link

At the bottom of the Discover Groups modal, enter a Telegram invite link
(e.g., `https://t.me/+abc123`) in the *Invite link* field and click *Join & Watch*.
The platform joins the group via TDLib and automatically adds it to the watch list.

NOTE: The account must be able to join the group. Restricted groups return an inline error.

==== Multi-Account Deduplication

When multiple accounts watch the same group, EMCIP deduplicates messages — each message
reaches the processing pipeline exactly once, regardless of how many accounts received it.

== Part II — REST API Reference

All API requests require the `Authorization: Bearer <token>` header unless marked as public. Obtain a token from §Authentication below.
Base URL on microk8s: `http://emcip.local/api`. For Docker Compose: `http://localhost:9087`.

=== Authentication

[cols="1,1,1,2"]
|===
|Method |Path |Auth |Description

|`POST`
|`/api/auth/token`
|None
|Issue a JWT
|===

==== Request

[source,json]
----
POST /api/auth/token
Content-Type: application/json

{
  "username": "admin",
  "password": "changeme"
}
----

==== Response

[source,json]
----
HTTP/1.1 200 OK
Content-Type: application/json

{
  "token": "eyJhbGciOiJIUzI1NiJ9..."
}
----

Use the token value in all subsequent requests:

[source,bash]
----
curl -H "Authorization: Bearer eyJhbGciOiJIUzI1NiJ9..." \
     http://emcip.local/api/api/tenants
----

Tokens expire after the duration configured in `app.jwt.expiration` (default: 24 hours). Re-authenticate to get a new token.

=== Telegram Accounts API

The Telegram Accounts API manages user-bot account lifecycle and group watch configuration.
All endpoints require `Authorization: Bearer <token>`.

==== Account Management

[cols="1,1,3"]
|===
|Method + Path |Description |Notes

|`GET /api/telegram/accounts`
|List accounts
|Returns array of `\{id, phoneNumber, status, createdAt}`

|`POST /api/telegram/accounts`
|Add account
|Body: `\{phoneNumber, displayName}`. Creates account in `UNCONFIGURED` state.

|`DELETE /api/telegram/accounts/\{id}`
|Remove account
|Permanent. Deletes the account record.

|`GET /api/telegram/accounts/\{id}/status`
|Get status
|Returns `\{id, status, lastError}`. Poll after code submission to detect `ACTIVE`.

|`POST /api/telegram/accounts/\{id}/reconnect`
|Start authentication
|Triggers TDLib to send a verification code to the account's phone number.
Returns 202. Account transitions to `AWAITING_CODE`.

|`POST /api/telegram/accounts/\{id}/code`
|Submit verification code
|Body: `\{code}`. Forwards the code to TDLib for verification. Returns 202.
Poll `/status` to confirm transition to `ACTIVE`.

|`POST /api/telegram/accounts/\{id}/password`
|Submit 2FA password
|Body: `\{password}`. Required only when the account has two-factor authentication enabled.
Returns 202.

|`POST /api/telegram/accounts/\{id}/logout`
|Log out account
|Terminates the TDLib session. Account transitions to `DISCONNECTED`. Returns 202.
|===

==== Group Watching

NOTE: All group discovery and watch endpoints require the account to be in `ACTIVE` status.

[cols="1,1,3"]
|===
|Method + Path |Description |Notes

|`GET /api/telegram/accounts/\{id}/chats`
|Discover groups
|Returns groups the account is a member of: `[\{chatId, title, memberCount, type}]`.
Account must be ACTIVE.

|`GET /api/telegram/accounts/\{id}/watched`
|List watched groups
|Returns `[\{chatId, groupProfileId, name, moderationLevel}]`.

|`POST /api/telegram/accounts/\{id}/watch`
|Watch a group
|Body: `\{chatId, title, memberCount}`. Returns 201 with GroupProfile. Idempotent.

|`DELETE /api/telegram/accounts/\{id}/watch/\{chatId}`
|Unwatch a group
|Returns 204. GroupProfile is not deleted (other accounts may reference it).

|`POST /api/telegram/accounts/\{id}/join`
|Join & watch by invite link
|Body: `\{inviteLink}`. Joins via TDLib then adds to watch list. Returns 201 with GroupProfile.
|===

==== Individual Service Health (port-forward)

Internal services (policy-engine, audit-service, etc.) are not exposed through the ingress. Use `kubectl port-forward` to reach their actuator endpoints:

[source,bash]
----
# Example: check policy-engine health
microk8s.kubectl port-forward svc/emcip-policy-engine -n emcip 9083:9083 &
curl -s http://localhost:9083/actuator/health | \
  python3 -c "import sys,json; d=json.load(sys.stdin); print(d.get('status','?'))"
kill %1
----

NOTE: For local Docker Compose development, all services are directly accessible on ports 9080–9087 and can be health-checked with a simple port loop.
See the _Docker Compose Guide_ §Observability for details.

==== Grafana & Loki

Grafana is available at `http://emcip.local/grafana` (default credentials: admin / admin).
Loki is the log aggregation backend — query it via Grafana → Explore → Loki datasource.

Three pre-built dashboards are provisioned automatically:

[cols="1,3"]
|===
|Dashboard |Shows

|*Service Health*
|Actuator UP/DOWN status per service, JVM heap used, GC pause time.

|*Kafka Consumer Lag*
|Consumer group lag per topic. Alert threshold: > 1000 messages.

|*Audit Throughput*
|Audit events/minute and moderation flags/minute over time.
|===
