## 1. Executive Summary

EMCIP is a well-structured microservice platform with 8 backend services, a shared library, a React SPA, and comprehensive observability infrastructure. The codebase is clean — no TODOs, no `System.out`, consistent Lombok usage, and good Kafka patterns.

**However, the project has accumulated technical debt in three areas:**

| Area | Severity | Summary |
|------|----------|---------|
| **Security** | CRITICAL | Default secrets in config, TDLib adapter has zero authentication, tenant isolation relies on spoofable headers, session tokens stored in plaintext |
| **Architecture** | HIGH | admin-api has no service layer (all logic in controllers), no input validation (`@Valid`), no global exception handler, ThreadLocal misuse in WebFlux |
| **UI** | MEDIUM | Auth token lost on page refresh, no logout button, silent error swallowing in Telegram polling, limited accessibility |

The multi-tenancy enforcement plan (already drafted) addresses the most critical data-isolation gap. This review identifies everything else.

## 3. Backend: emcip-admin-api

**Port**: 9087 | **Stack**: WebFlux + R2DBC + Spring Security + JWT
**Role**: API gateway connecting UI to all backend services
**9 controllers, 44 endpoints, 5 entities, 5 repositories, 4 external service clients**

### 3.1 Critical Issues

| # | Issue | Severity | Details |
|---|-------|----------|---------|
| A1 | **No service layer** | HIGH | All business logic lives in controllers. Controllers do data access, external calls, Kafka publishing, and error handling. Violates SRP, makes testing harder, prevents reuse. |
| A2 | **No input validation** | HIGH | Zero `@Valid`/`@Validated` annotations. No `@NotNull`, `@NotBlank`, `@Min`, `@Max` on DTOs. Manual null/blank checks scattered in 3 controllers; the other 6 accept anything. |
| A3 | **No global exception handler** | HIGH | No `@RestControllerAdvice`. Errors leak stack traces and produce inconsistent response formats. |
| A4 | **ThreadLocal in WebFlux** | HIGH | `TenantContext` uses `ThreadLocal` but admin-api is reactive (WebFlux). Reactor can switch threads between operators, causing tenant context loss or cross-contamination. Should use Reactor `Context` instead. |
| A5 | **No pagination enforcement** | MEDIUM | `Flux` returns all results. `size` param is advisory only (default 50, no upper bound). Large datasets → OOM. |
| A6 | **No WebClient timeouts** | MEDIUM | External service calls (TDLib, policy-engine, moderation, audit, orchestrator) have no read/connect timeout configured. A slow downstream service blocks the caller indefinitely. |
| A7 | **No circuit breaker** | MEDIUM | No resilience4j or similar. One downed service cascades failures to admin-api. |
| A8 | **Silent error masking** | MEDIUM | Multiple `onErrorResume()` handlers return `Mono.empty()` without logging, masking failures from downstream services. |
| A9 | **No API versioning** | LOW | URLs are `/api/...` with no version prefix. Breaking changes affect all clients simultaneously. |
| A10 | **CORS `/**` wildcard** | LOW | CORS registered for both `/api/**` and `/**`. The wildcard `/**` is unnecessary and could expose actuator endpoints to cross-origin requests. |

### 3.2 What's Working Well

- JWT + ServiceToken dual-auth is a solid pattern
- Tenant-aware repositories exist (scoped by `findAllByTenantId`)
- OpenAPI/Swagger properly configured with JWT bearer scheme
- Kafka producer for simulation uses `acks=all` + idempotence
- TelegramSessionResumeRunner handles startup reconnection with retry
- All 9 controllers + 2 security classes have unit tests

### 3.3 Recommendations

1. **Extract service layer** — Create `GroupProfileService`, `TelegramAccountService`, `SimulationService` etc. Controllers should only do request/response mapping.
2. **Add `@ControllerAdvice`** — Centralized error handler returning consistent `ProblemDetail` (RFC 9457).
3. **Replace ThreadLocal** — Use `Mono.deferContextual()` / `ReactiveSecurityContextHolder` for tenant propagation in WebFlux.
4. **Add validation** — `@Validated` on controllers, Jakarta Validation on DTOs.
5. **Configure WebClient timeouts** — `responseTimeout(Duration.ofSeconds(10))` on each WebClient.

## 6. Architecture Review

### 6.1 Strengths

- **Event-driven pipeline** — clean unidirectional Kafka flow, no circular dependencies
- **Observability stack** — Prometheus + Grafana + Loki + Tempo, pre-provisioned dashboards
- **GraalVM native support** — 3 services have native image builds
- **Multi-stage Docker builds** — well-optimized, non-root users, health checks
- **Comprehensive documentation** — C4 diagrams, ADRs, AsciiDoc guides, planning docs
- **Testcontainers usage** — real database/Kafka in integration tests

### 6.2 Gaps

| # | Gap | Impact | Recommendation |
|---|-----|--------|----------------|
| G1 | **No service layer in admin-api** | Testability, reuse, SRP violation | Extract business logic to service classes |
| G2 | **ThreadLocal for tenant in WebFlux** | Thread-safety issues, potential cross-tenant data leaks | Use Reactor `Context` for reactive services |
| G3 | **Mixed JPA + R2DBC** | Cognitive overhead, different patterns for same operations | Document clearly which services use which and why (partially done in ADRs) |
| G4 | **No API gateway** | admin-api acts as both gateway and business service | Consider Spring Cloud Gateway or similar for cross-cutting concerns (auth, rate-limiting, CORS) |
| G5 | **No schema registry** | Kafka event schemas defined in Java only; no runtime validation between producer/consumer versions | Consider Confluent Schema Registry or equivalent |
| G6 | **Shared PostgreSQL instance** | All services use same `emcip` database; schema collisions possible, no resource isolation | Separate databases per service (or at least separate schemas) |
| G7 | **No retry/circuit-breaker for HTTP clients** | admin-api → downstream service failures cascade | Add resilience4j or Spring Retry |
| G8 | **Policy engine Liquibase disabled** | Schema drift vs. other services | Enable Liquibase or create explicit "read-only" schema contract |

### 6.3 Architecture Decision Debt

- **ADR-004 (R2DBC)** → Decision to use R2DBC for some services but JPA for others creates two patterns. ADR-007 deferred the resolution. Consider standardizing on one.
- **No ADR for tenant isolation strategy** — The multi-tenancy plan exists but no ADR documents the ThreadLocal vs Reactor Context tradeoff.
- **No ADR for auth/authz model** — JWT + service token + tenant header is complex enough to warrant one.

## 7. Trivy / CVE Context

### 7.1 Why 1000+ Alerts

The alert count is driven by **three categories**:

| Source | Approximate % | Explanation |
|--------|---------------|-------------|
| **TDLib native libraries (C/C++)** | ~60-70% | The `tdlib-adapter` Dockerfile builds TDLib from source (`git clone --depth 1 https://github.com/tdlib/td`). This pulls in OpenSSL, zlib, glibc, and the entire TDLib C++ codebase. Trivy scans the OS packages (libssl3, zlib1g) and the compiled binaries, flagging every CVE in those C libraries. |
| **GraalVM native images** | ~15-20% | Services using `Dockerfile.native` (conversation-context, policy-engine, llm-orchestrator) are based on `debian:12-slim` which includes system libraries. GraalVM's `native-image-community:25.0.1` base also has C library CVEs. |
| **JRE/OS packages** | ~10-15% | `eclipse-temurin:21-jre` images include OS-level packages that Trivy scans. |
| **Java dependencies** | ~5% | Spring Boot 4.0.5, Jackson, etc. |

### 7.2 Spring Boot 4.0.5 Status

Spring Boot 4.0.5 was released recently. Check for updates:
- **Spring Boot 4.0.6** or newer may have been released since. Run `mvn versions:display-dependency-updates` to check.
- Spring Boot 4.x is on the **Jakarta EE 11** track, which is current.

### 7.3 Recommendations for Trivy

| Action | Impact on Alert Count | Effort |
|--------|----------------------|--------|
| **Suppress C/C++ findings for tdlib-adapter** — create `.trivyignore` for known OS-level CVEs that aren't exploitable in this context | -60% | LOW |
| **Pin and update base images** — `eclipse-temurin:21.0.x-jre-noble` instead of floating `21-jre` | -10% | LOW |
| **Use distroless or Alpine for JVM services** — fewer OS packages = fewer CVEs | -20% | MEDIUM |
| **Update GraalVM** — pinned at 25.0.1 due to SIGSEGV bug in 25.0.2; monitor for 25.0.3 | -5% | LOW (when available) |
| **Separate Trivy categories** — use `--vuln-type os,library` separately; triage OS CVEs vs Java CVEs | Clarity | LOW |
| **Add `.trivyignore` for accepted risks** — document each suppression with justification | Reduces noise | LOW |
