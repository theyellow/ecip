# P3.5a — Required Status Checks on `main` Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make a red or absent CI build actually block a merge to `main`, without making docs-only PRs unmergeable.

**Architecture:** Path filtering moves out of `maven.yml`'s `pull_request` trigger and into the workflow, behind a fail-closed `dorny/paths-filter` negation. A new always-running aggregator job, `ci-gate`, reports one conclusion for the whole Maven workflow and becomes the required status check, alongside `trufflehog`. The ruleset gains a `required_status_checks` rule plus a repo-admin `pull_request`-mode bypass, and its payload is checked into the repository.

**Tech Stack:** GitHub Actions, `dorny/paths-filter@v4`, GitHub Repository Rulesets REST API via `gh`.

**Spec:** `docs/superpowers/specs/2026-08-08-p3.5a-required-status-checks-design.md`

## Global Constraints

- The **only** repository to touch is `theyellow/ecip`; the ruleset is id **`15118295`**, name `Branchruleset`, target `refs/heads/main`.
- **Sequencing is mandatory:** `ci-gate` must have reported on at least one PR *before* the ruleset requires it. Requiring a never-reported context deadlocks every open PR, including the one adding it.
- Required contexts are exactly **`ci-gate`** and **`trufflehog`**. Not `build`, not `code-quality`, not `Analyze Java`.
- `strict_required_status_checks_policy` is **`false`** (non-strict — no forced rebase before merge).
- Bypass is **repo admin, `bypass_mode: "pull_request"`** — never `"always"` (that would re-open direct pushes to `main`, which the ruleset exists to close).
- The `code` path filter must be **fail-closed**: any path not explicitly named as documentation counts as code and runs the build. Never convert it to an allowlist of code paths.
- `skipped` upstream jobs must **pass** `ci-gate`; `failure` and `cancelled` must fail it.
- Do **not** touch `push.paths-ignore` in `maven.yml`, `codeql.yml`, `secret-scanning.yml`, or `build-images.yml`.
- Do **not** remove the duplicated `spotless`/`pmd` steps from `code-quality` in this work — it is filed as a follow-up in Task 6.
- Every proof in Task 5 must be **observed and pasted into the PR description**. A gate that has not been seen to fail is not a gate (P3.4 verification lesson).

- [ ] **Step 3: Add the `changes` job**

Insert directly after `jobs:` (line 21), before `build:`:

```yaml
jobs:
  # Decides whether this PR touches anything that needs a build. Expressed as
  # negations with predicate-quantifier 'every' (a file counts only if it matches
  # ALL patterns), so the filter is fail-closed: any path not named below — including
  # one nobody anticipated — is treated as code and runs the full build. An allowlist
  # of code paths would fail open, which is the defect class recorded in P3.4.
  changes:
    runs-on: ubuntu-latest
    outputs:
      code: ${{ steps.filter.outputs.code }}
    steps:
      - uses: actions/checkout@v7

      - uses: dorny/paths-filter@v4
        id: filter
        with:
          predicate-quantifier: 'every'
          filters: |
            code:
              - '!docs/**'
              - '!documentation/**'
              - '!helm/**'
              - '!**/*.md'
              - '!.github/workflows/build-images.yml'

      - name: Report decision
        run: echo "code=${{ steps.filter.outputs.code }}"
```

- [ ] **Step 4: Gate `build` and `code-quality` on the filter**

    runs-on: ubuntu-latest
```

In `code-quality:` (was line 69), identically:

- [ ] **Step 5: Add the `ci-gate` aggregator at the end of the file**

Append to `.github/workflows/maven.yml`:

```yaml

  # The single required status check for this workflow (P3.5a). It runs on every PR
  # without exception, so it always reports a conclusion and can never deadlock a PR.
  #   skipped   -> passes (the docs-only path; that is the whole point)
  #   failure   -> fails
  #   cancelled -> fails
  # `changes` is in `needs` so that a failure of the filter job itself fails the gate
  # rather than skipping the build and reporting green.
  ci-gate:
    name: ci-gate
    if: always()
    needs: [changes, build, code-quality]
    runs-on: ubuntu-latest
    steps:
      - name: Check upstream job results
        run: |
          echo "results: ${{ join(needs.*.result, ',') }}"
          if [[ "${{ contains(needs.*.result, 'failure') }}" == "true" ]]; then
            echo "::error::An upstream job failed"
            exit 1
          fi
          if [[ "${{ contains(needs.*.result, 'cancelled') }}" == "true" ]]; then
            echo "::error::An upstream job was cancelled"
            exit 1
          fi
          echo "All upstream jobs succeeded or were skipped"
```

# Branch protection — `main`

`main` is protected by repository ruleset **`Branchruleset`** (id `15118295`).
The payload is checked in at `.github/rulesets/main.json`, which is the source of
truth; the live ruleset must match it.

## What is enforced

| Rule | Effect |
|---|---|
| `deletion` | `main` cannot be deleted |
| `non_fast_forward` | no force-pushes to `main` |
| `pull_request` (0 approvals) | all changes arrive via PR |
| `required_status_checks` | `ci-gate` and `trufflehog` must pass; non-strict |

**`ci-gate`** is an aggregator job in `.github/workflows/maven.yml`. It runs on every
PR without exception and reports one conclusion for the whole Maven workflow.
Upstream jobs that are *skipped* (docs-only PRs) pass it; *failed* or *cancelled*
jobs fail it. It exists because a workflow prevented from triggering by a `paths`
filter reports no status at all, and a required check that never reports blocks the
PR forever. Never require `build` or `code-quality` directly.

**Non-strict** means a PR need not be rebased onto current `main` before merging. Two
PRs green in isolation but broken together are caught by the push-to-`main` run, not
by the gate. Revisit if PR concurrency rises.

`Analyze Java` (CodeQL) is deliberately **not** required: it is slow and alert-driven,
and its findings are triaged in the Security tab rather than acting as a merge signal.

## When CI is down

A GitHub Actions outage means required checks never report and nothing can merge.
This is intended: PR #229 merged during the 2026-08-06 outage with zero checks, which
is what prompted P3.5a. Two options, in order of preference:

1. **Wait.** Almost always correct.
2. **Repo admins** may merge via the PR bypass (`bypass_mode: "pull_request"`).
   Bypasses are recorded in the ruleset audit log. Use deliberately, not routinely.

Last resort, if the bypass is unavailable:

```bash
gh api --method PUT repos/theyellow/ecip/rulesets/15118295 -f enforcement=evaluate
# ... merge, then IMMEDIATELY:
gh api --method PUT repos/theyellow/ecip/rulesets/15118295 -f enforcement=active
```

## Verifying the gate still works

A gate that has not been seen to fail is not a gate. After any change to `ci-gate`,
`maven.yml`'s triggers, or the ruleset, re-run the P3.5a proofs: a PR with a failing
test must show `mergeStateStatus: "BLOCKED"`, and a docs-only PR must show
`"CLEAN"` with `build` skipped.
```

If Task 4 Step 5's fallback applied and there is no admin bypass, replace option 2 above with a note that no bypass exists and the `evaluate` procedure is the only escape hatch.
