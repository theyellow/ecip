# P2.4 — LLM/Markdown Render Sanitization (defense-in-depth)

> Status: **design approved**, ready for implementation plan
> Date: 2026-07-31
> Backlog: RT2-011 / RT2-012 (§0a, P2.4, size S)
> Findings: `documentation/RED_TEAM_REPORT_2026-07-18.md` RT2-011 (`ReportViewer.jsx`), RT2-012 (`Flags.jsx:251`)
> Module: `emcip-admin-ui` (React SPA)

---

## 1. Problem statement & honest threat model

The red-team flagged two admin-ui components that render LLM-generated content:

- **RT2-011** — `ReportViewer.jsx`: `renderMarkdownLines()` renders `report.content` (LLM research reports).
- **RT2-012** — `Flags.jsx:251`: `<div>{msg.content}</div>` renders LLM chat responses.

**Verified against current `main` before designing:**

1. Neither component uses `dangerouslySetInnerHTML`. A grep of the entire frontend
   (`dangerouslySetInnerHTML`, `innerHTML`, `insertAdjacentHTML`,
   `createContextualFragment`) returns **zero HTML sinks**.
2. Both sinks render content **exclusively through React text nodes**
   (`{line}`, `{item}`, `{msg.content}`). React auto-escapes text nodes, so
   `<script>`, `<img onerror>` etc. render as inert literal text today.
3. The red-team's "exploitable" qualifier leaned on *"combined with missing CSP"* —
   and CSP was delivered in **P2.3 (PR #217)**.

**Conclusion:** there is **no HTML/JS XSS vector today**. A literal
`DOMPurify.sanitize()` wrapper on these strings would be a **no-op** — DOMPurify
sanitizes HTML before an HTML sink, and this content never becomes HTML.

**What React escaping does *not* cover — the genuine, active mitigation:**
Unicode-level attacks in LLM text that React passes through unchanged because they
are "valid" text:

- **Bidirectional overrides / Trojan-Source** (`U+202A–202E`, `U+2066–2069`) —
  visually reorder text an operator reads to make moderation/research decisions.
- **Zero-width / invisible characters** (`U+200B–200D`, `U+2060`, `U+FEFF`) —
  smuggle hidden content or obscure text.
- **C0/C1 control characters** — layout/terminal corruption when copied.

This is why P2.4 is **defense-in-depth, not theater**: the DOMPurify layer is
checklist-mandated forward-cover for any *future* HTML sink, while **Unicode
hygiene is the active mitigation** that closes a real (if lower-severity) gap.

## 2. Design decisions (approved)

| # | Decision | Choice | Rationale |
|---|----------|--------|-----------|
| D1 | Direction | **Defense-in-depth wrap** (not rich-markdown, not doc-only) | Keep safe text-node rendering; add a thin normalization layer + written rationale so RT2-011/012 close with evidence. |
| D2 | Dependency | **Add `dompurify`** *and* a dependency-free Unicode-hygiene pass | Literally satisfies the checklist item and pre-covers a future HTML sink; hygiene does the real work today. |
| D3 | Non-render paths | **Sanitize everywhere** — render + `.md` download + Copy button | Safety over artifact fidelity: bidi/zero-width must not ride into a pasted context or saved file. Trade-off: intentional inline HTML in a downloaded `.md` is stripped. |
| D4 | Length cap | **No cap** | Research reports are legitimately long; a cap risks silently truncating real content. |

## 3. The critical implementation gotcha (must not regress)

DOMPurify **HTML-encodes** its output (it is designed for insertion via
`innerHTML`). If we naively write `{DOMPurify.sanitize(msg.content)}` into a React
**text node**, React escapes the already-encoded string **again**:

```
input : "A & B where x > y"
DOMPurify.sanitize(...)      -> "A &amp; B where x &gt; y"   (encoded for innerHTML)
React text node re-escapes   -> renders literally: "A &amp; B where x &gt; y"   [CORRUPTED]
```

LLM research reports are full of `&`, `<`, `>`, quotes, and code, so a naive
"security fix" would **visibly corrupt every report**. The design pins the
**strip-tags-to-plain-text** path that avoids double-encoding:

```
DOMPurify.sanitize(raw, { ALLOWED_TAGS: [], ALLOWED_ATTR: [],
                          KEEP_CONTENT: true, RETURN_DOM: true }).textContent
```

`RETURN_DOM` returns a sanitized DOM node; reading `.textContent` yields **decoded
plain text** (entities resolved, tags removed, tag *contents* kept). React then
escapes exactly once — correct output.

## 4. Component design

### 4.1 `src/utils/sanitizeText.js` (new — single purpose)

Uses explicit `\u` escapes (not literal invisible characters) so the source is
readable and diff-safe.

```js
import DOMPurify from 'dompurify'

// C0 (minus \t \n \r) + C1 control chars.
// eslint-disable-next-line no-control-regex
const CONTROL = /[\u0000-\u0008\u000B\u000C\u000E-\u001F\u007F-\u009F]/g
// Zero-width space/non-joiner/joiner, word-joiner, BOM.
const ZERO_WIDTH = /[\u200B-\u200D\u2060\uFEFF]/g
// Bidi embeddings/overrides + isolates (Trojan-Source).
const BIDI = /[\u202A-\u202E\u2066-\u2069]/g

/**
 * Sanitize LLM-generated text for display, download, or clipboard.
 *
 * There is no HTML sink in this app (content is rendered via React text nodes),
 * so the DOMPurify pass is defense-in-depth forward-cover for any future HTML
 * sink. The active mitigation is the Unicode hygiene pass, which removes
 * bidi/zero-width/control characters that React escaping does NOT neutralize.
 *
 * DOMPurify is invoked with RETURN_DOM + textContent (not the default string
 * return) so its HTML-encoded output does not get double-escaped by React.
 */
export function sanitizeText(raw) {
  if (typeof raw !== 'string') return ''
  const stripped =
    DOMPurify.sanitize(raw, {
      ALLOWED_TAGS: [],
      ALLOWED_ATTR: [],
      KEEP_CONTENT: true,
      RETURN_DOM: true,
    }).textContent ?? ''
  return stripped.replace(CONTROL, '').replace(ZERO_WIDTH, '').replace(BIDI, '')
}
```

**Pipeline order:** DOMPurify strip-tags (→ decoded plain text) → Unicode hygiene
regexes. `\n`/`\t` are preserved, so downstream line-splitting in ReportViewer
still works. Bidi/zero-width chars are valid text that `textContent` preserves,
so the regex pass is what removes them.

**What it does NOT do:** it does not decode markdown, does not truncate, does not
alter ordinary printable text (plain input is returned unchanged apart from the
removed hostile characters).

### 4.2 Wiring — the sinks

| File | Path | Change |
|------|------|--------|
| `ReportViewer.jsx` | render | `renderMarkdownLines(sanitizeText(report.content))` — sanitize once, then split lines |
| `ReportViewer.jsx` | download (`handleDownload`) | blob from `sanitizeText(report.content)` |
| `Flags.jsx` | render (`:251`) | `<div>{sanitizeText(msg.content)}</div>` |
| `Flags.jsx` | copy (`copyMessage`) | `copyMessage(sanitizeText(msg.content))` (or sanitize inside the handler) |

No other frontend files render LLM content (verified: `Flags.jsx`'s
`analysisModel`/`copyAnalysisBtn` are style-name reuse, not extra sinks).

## 5. Testing

### 5.1 `sanitizeText.test.js` (unit — the core evidence)

- `<script>alert(1)</script>Hello` → `Hello` (tag stripped, content kept).
- `<img src=x onerror=alert(1)>` → `''` / no attributes survive.
- **Double-encode regression guard:** `A & B where x > y and q="z"`
  round-trips to the *literal* string (no `&amp;`, `&gt;`, `&quot;`).
- Bidi override (input with a `\u202E` char) → bidi char removed.
- Zero-width (`a\u200Bb\uFEFFc`) → `abc`.
- Control chars (`a\u0000b`) → `ab`; `\t`/`\n` **preserved**.
- Plain multi-line markdown text unchanged (headings/bullets survive as text).
- Non-string input (`null`, `undefined`, number, object) → `''`.

### 5.2 Component smoke tests

- **ReportViewer**: given `report.content` containing a `<script>` line plus
  `## Heading` and `A & B`, renders heading + inert, correctly-decoded text
  (asserts no `<script>` element and no `&amp;` in the DOM text).
- **Flags**: given an assistant `msg.content` with a hostile+entity payload,
  the chat bubble shows inert decoded text.

Runner: existing `vitest` + `jsdom` (DOMPurify operates against the jsdom
`window`; no extra test config needed since the render path already runs in jsdom).

## 7. Out of scope (deliberately)

- **Rich markdown rendering** (bold/links/code/tables via `react-markdown`/`marked`).
  That would introduce a *real* HTML sink where DOMPurify does active work — a
  separate, larger UX item, not this security remediation. Logged as a possible
  future enhancement, not P2.4.
- **P2.7 `npm audit`** (RT2-015) will pick up `dompurify` in its dependency sweep.

1. `sanitizeText()` exists, is DOMPurify-backed, and passes §5.1.
2. All four paths (2 renders, 1 download, 1 copy) route through `sanitizeText()`.
3. No report/chat text with `&`, `<`, `>`, or quotes renders double-encoded.
4. Bidi/zero-width/control characters are absent from rendered, downloaded, and
   copied output.
