# P2.8 — Failed-login audit + admin audit-trail persistence

- **Backlog**: S-OPEN-3 / RT-017 (`documentation/RED_TEAM_REPORT_2026-07-18.md`, `REVIEW-2026-07-18.md`)
- **Phase**: P2.8 (last item before P3 pre-1.0.0)
- **Date**: 2026-08-03
- **Branch**: `feat/p2.8-failed-login-audit`
- **Modules**: `emcip-admin-api`, `emcip-audit-service`

## Summary

Publish a `LOGIN_FAILURE` audit event on failed admin login. While verifying the
finding's premise, we discovered the admin audit trail does **not** persist
end-to-end: `AdminAuditPublisher` publishes to the `audit.events` Kafka topic, but
**nothing consumes it**. So this work also wires up an `audit.events` consumer in
audit-service, making *all* admin audit events (`LOGIN_SUCCESS`, `ACCESS_DENIED`,
`USER_*`, `PASSWORD_CHANGED`, FlagService's events, and the new `LOGIN_FAILURE`)
actually reach the `audit_events` table. This is the true closure of RT-017 —
which was previously marked "MOSTLY FIXED" on the strength of the publisher merely
*existing and being called* (publish ≠ persist).

## Premise corrections (verify-first)

1. **No `BadCredentialsException`.** admin-api does not use Spring Security's
   `AuthenticationManager` for login. `AuthService.authenticate` is a hand-rolled
   reactive flow: `findByUsername → filter(enabled && passwordEncoder.matches) →
   switchIfEmpty(ResponseStatusException 401)`. The failure hook is that branch,
   not an exception handler.
2. **`audit.events` has no consumer.** audit-service's `AuditEventConsumer` listens
   only to five *domain* topics (`telegram.raw.messages`, `messages.classified`,
   `policies.decisions`, `responses.generated`, `moderation.flags`). No pattern
   listener (only `^.*\.dlq$`), no second consumer class, no REST ingestion
   (audit-service `AuditController` is read-only). Admin audit events published to
   `audit.events` are dropped on the floor.
3. **Tenant is silently dropped.** `EventSchemas.AuditEvent` has no `tenantId`
   field, and `AdminAuditPublisher.publish(...)` accepts a `tenantId` param but
   never puts it in the event or a Kafka header. The consumer's
   `validateTenantHeader` is fail-closed (rejects records without a valid tenant
   header), so tenant attribution requires adding a tenant Kafka header at publish.
4. **Generic consumer flattens semantics:** `.action(event.eventType())` (→
   `"Audit"`, losing `LOGIN_FAILURE`) and `.outcome("PROCESSED")` (losing
   `FAILURE`). The `audit.events` mapping must preserve these.

## Design decisions (agreed during brainstorming)

| # | Decision |
|---|----------|
| Scope | Fix the trail end-to-end in one P2.8 PR (consumer + tenant header + outcome param + `LOGIN_FAILURE`). Realistically size **M**, not S. |
| Failure reason | Distinguish `USER_NOT_FOUND` / `BAD_PASSWORD` / `DISABLED`, recorded in audit `details.reason` (internal only). |
| Client response | Identical generic `401 "Invalid credentials"` for all three reasons — no enumeration oracle to the client. |
| IP | Leftmost `X-Forwarded-For` token if present (`ipSource=XFF`), else socket `remoteAddress` (`ipSource=SOCKET`). XFF is only trustworthy behind a trusted ingress/BFF — documented, not enforced here. Also fixes the `LOGIN_SUCCESS` `"request-context"` placeholder. |
| Username hygiene | Trim to 256 chars + strip Unicode Cc/Cf (control/bidi/zero-width) before it enters the event (attacker-controlled, may be PII/email, immutable table). |
| Tenant attribution | `BAD_PASSWORD`/`DISABLED` → the resolved user's `tenantId`; `USER_NOT_FOUND` → `null` (→ `GLOBAL_TENANT_SENTINEL`). Failed logins against a tenant's user surface in that tenant's audit view; the weak existence-oracle is only readable by that tenant's own admins. |
| `ACCESS_DENIED` outcome | Fix in this PR: `"SUCCESS"` → `"DENIED"` (it's a denial). |
| `actorType` (admin events) | `"ADMIN"` (generic domain path uses `"SYSTEM"`). |
| Consumer offset | `auto.offset.reset=latest` — the new consumer must not replay the accumulated unconsumed `audit.events` backlog (which includes header-less historical FlagService events that would DLQ). Persist from deploy forward. |

## Components

### 1. `AdminAuditPublisher` (admin-api) — carry outcome + tenant header

- Add a 7-arg overload `publish(action, resourceType, resourceId, actor, tenantId, details, outcome)`.
  The existing 6-arg method delegates with `outcome = "SUCCESS"` (no churn to
  `USER_*` / `LOGIN_SUCCESS` callers).
- Build a `ProducerRecord<>("audit.events", resourceId, json)`, call
  `TenantAwareKafkaSupport.addTenantHeader(record, tenantId)` (maps
  `null → GLOBAL_TENANT_SENTINEL`), then `kafkaTemplate.send(record)`.
- Keep the existing try/catch — audit publishing must never break the operation.
- **`ACCESS_DENIED`** (in `SecurityConfig`): switch its call to the 7-arg overload
  with `outcome = "DENIED"`.
- **`FlagService`** (two raw `audit.events` sends at ~L374/L395): they emit ad-hoc
  JSON (no `eventId`, `details` not `changes`, no tenant header) and inject no
  `AdminAuditPublisher` — an inline header add is insufficient (null `eventId`
  would break persistence/dedupe). Fix minimal-correct: inject `AdminAuditPublisher`
  and route both through `publish(action, "Flag", flagId, "system", null, details,
  "SUCCESS")` — this generates a proper `eventId`, sets the tenant header
  (`null → GLOBAL_TENANT_SENTINEL`), and maps `details → changes`. Real
  operator/tenant attribution for flag audit events is deferred to **BACKLOG §0b
  P2.8-F2** (FlagController/FlagService don't thread username/tenant today).

### 2. audit-service — consume `audit.events`

- New `@KafkaListener(topics = "audit.events", groupId = "emcip-audit-service",
  containerFactory = "kafkaListenerContainerFactory")` → `handleAdminAuditEvent`.
- A **dedicated** mapping method (parallel to `processAuditEvent`, reusing its
  tenant-validation + `saveWithChain` + duplicate-skip logic) that **preserves**:
  - `action = event.action()`
  - `actor` / `actorId = event.actor()`, `actorType = "ADMIN"`
  - `outcome = event.outcome()`
  - `resourceType = event.resourceType()`, `resourceId = event.resourceId()`
  - `details = event.changes()`
  - `correlationId = event.eventId()` (admin events have no `sourceEventId`)
  - `sourceService = "emcip-admin-api"`
  - `tenantId = validateTenantHeader(record)`
- Consumer config: `auto.offset.reset=latest` for this listener/group so the
  historical backlog is not replayed. (Verify how the container factory sets
  offset-reset; if it is global, isolate this listener's group config.)

### 3. `AuthService.authenticate` (admin-api) — `LOGIN_FAILURE` with reason

Restructure the failure branch to distinguish reasons while keeping the response
generic:

```
findByUsername(username)
  .flatMap(user ->
      !user.isEnabled()                             ? fail(DISABLED,   user.getTenantId())
    : !passwordEncoder.matches(pw, user.getHash())  ? fail(BAD_PASSWORD, user.getTenantId())
    :                                                 success(user))
  .switchIfEmpty(Mono.defer(() -> fail(USER_NOT_FOUND, null)))
```

- `fail(reason, tenantId)` publishes
  `LOGIN_FAILURE` with `outcome="FAILURE"`, `actor`/`resourceId = sanitizeAudit(username)`,
  `details = {reason, ip, ipSource}`, then emits the **same**
  `ResponseStatusException(401, "Invalid credentials")` for all reasons.
- `authenticate(...)` signature gains `clientIp` + `ipSource` (or a small
  `ClientContext` record) passed from the controller — keeps `AuthService` free of
  web types.
- `LOGIN_SUCCESS` `details` updated to the real `{ip, ipSource}` (replaces the
  `"request-context"` placeholder).

### 4. Client-IP helper (admin-api)

`ClientIp.resolve(ServerHttpRequest) → (String ip, String source)`:
- If `X-Forwarded-For` present → leftmost comma-token, trimmed; `source = "XFF"`.
- Else `remoteAddress` host; `source = "SOCKET"`.
- `AuthController.token(...)` (and any other login entry) resolves it from the
  exchange and passes it into `authenticate(...)`.

### 5. Audit-hygiene helper (admin-api)

`sanitizeAudit(String) → String`: trim to ≤256 chars, strip Unicode categories
`Cc` (control) and `Cf` (format: bidi/zero-width). The Java sibling of P2.4's
frontend `sanitizeText`. Applied to the attempted username before it enters the
event.

## Testing

### audit-service (Testcontainers IT — reuse the existing audit IT harness)
- Publish an `AuditEvent` with a valid tenant header to `audit.events` → a row is
  persisted in `audit_events` with the **preserved** `action`, `actor`, `outcome`,
  and `tenantId`.
- Publish **without** a tenant header → record is **rejected** (fail-closed), no row.
- (If cheap) a `LOGIN_FAILURE`-shaped event persists `outcome="FAILURE"` and the
  `reason` detail survives serialization.

### admin-api (unit)
- `AuthService`: each of `USER_NOT_FOUND` / `BAD_PASSWORD` / `DISABLED` publishes
  `LOGIN_FAILURE` with `outcome="FAILURE"`, the correct `reason`, and tenant per the
  rule (resolved id vs null); every case returns an **identical** 401.
- `AuthService`: SUCCESS still publishes `LOGIN_SUCCESS` and now carries real
  `{ip, ipSource}`.
- `AdminAuditPublisher`: tenant header present (= `GLOBAL_TENANT_SENTINEL` when
  `tenantId` null); `outcome` carried through; 6-arg overload defaults `"SUCCESS"`.
- `ClientIp`: XFF-present → leftmost token + `XFF`; absent → socket host + `SOCKET`.
- `sanitizeAudit`: >256 truncated; control/bidi/zero-width stripped; benign text
  untouched.

## Error handling

- Audit publish failures never break login (existing publisher try/catch retained).
- Consumer failures use the existing retry → DLQ path (`DefaultErrorHandler`).
- FlagService tenant-header fix prevents its events being DLQ'd by the new
  fail-closed consumer.
