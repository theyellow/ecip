# P3.5a — Require status checks on `main`

**Date**: 2026-08-08
**Roadmap item**: P3.5a (`documentation/ROADMAP.md`, tier ① CI net) — ID `CI-GATE`
**Status**: design approved, pending implementation plan

---

## Problem

The `Branchruleset` ruleset (id `15118295`, enforcement `active`) protects
`refs/heads/main` with three rules — `deletion`, `non_fast_forward`, and
`pull_request` (0 required approvals). It has **no `required_status_checks` rule**.

Consequence: every CI job in this repository *reports* but nothing *gates*. A pull
request whose build is red, or whose workflows never ran at all, merges exactly as
easily as a green one. PR #229 merged during the 2026-08-06 GitHub Actions outage
with zero checks reported, which is what surfaced this.

This makes the work of P3.1 (integration tests in CI), P3.2 (frontend tests in CI)
and P3.3 (`@PreAuthorize` e2e test) advisory rather than enforcing. Those items are
only worth what the gate around them is worth, and today that is nothing.

It is also the same defect class as P3.1 and P3.4: machinery that exists, looks
correct, and does not do the job it appears to do.

## Current state (verified 2026-08-08)

Ruleset `15118295`:

```
rules:        deletion, non_fast_forward, pull_request(0 approvals)
bypass_actors: []
current_user_can_bypass: "never"
```

Workflows and the check names they produce on a PR to `main`:

| Workflow | File | Check name(s) | PR trigger |
|---|---|---|---|
| Java CI with Maven | `.github/workflows/maven.yml` | `build`, `code-quality` | PR → main, **with `paths-ignore`** |
| CodeQL | `.github/workflows/codeql.yml` | `Analyze Java` | PR → main, no path filter |
| Secret Scanning | `.github/workflows/secret-scanning.yml` | `trufflehog` | PR → main, no path filter |
| Build and Push Docker Images | `.github/workflows/build-images.yml` | — | push/tag only; never a PR check |

The `maven.yml` jobs declare no `name:`, so their check names are the job ids
`build` and `code-quality`.

`maven.yml`'s `pull_request` trigger carries `paths-ignore: docs/**,
documentation/**, helm/**, *.md, .github/workflows/build-images.yml`.

## The constraint that shapes the design

GitHub treats two situations differently:

- a job **skipped by an `if:` expression** reports a `skipped` conclusion, which
  *satisfies* a required status check;
- a workflow **never triggered** because of a `paths` / `paths-ignore` filter reports
  **nothing at all**, and the required check sits permanently at
  *"Expected — waiting for status to be reported"*.

So naming `build` as a required check would make every docs-only PR unmergeable
forever. This repository merges docs-only PRs routinely (`ROADMAP.md`,
`BACKLOG.md`, specs), and with `bypass_actors: []` there would be no way out —
not even for the repository owner.

## Decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | Path filtering moves **from the trigger into the workflow**, behind an aggregator job named `ci-gate` which is the required check | The only shape that both skips docs PRs quickly and always reports a conclusion |
| D2 | Required set is **`ci-gate` + `trufflehog`** | Covers "the build is green" and "no verified secret is being committed" — the latter being the one class of mistake that cannot be undone after merge. CodeQL stays advisory: it is slow, alert-driven, and its findings are triaged in the Security tab (see the accepted `java/spring-disabled-csrf-protection` false positive), which is not a merge signal |
| D3 | **Non-strict** (`strict_required_status_checks_policy: false`) | Strict mode forces an update-rebase-rerun cycle on every merge whenever `main` has moved. The gap it leaves — two PRs green in isolation, broken together — is caught by the push-to-`main` run of the same workflows, acceptable at this repo's concurrency. Merge queues are the real fix and are out of scope |
| D4 | **Repo-admin bypass in `pull_request` mode** | Required checks turn an Actions outage into a total merge freeze — precisely the 2026-08-06 scenario. `pull_request` mode grants an audited override via the PR flow only; it does not re-open direct pushes to `main`, which the ruleset exists to close |
| D5 | The `code` path filter is expressed as **negations, fail-closed** | An allowlist of code paths would silently skip CI for any path nobody thought of. Fail-open filters are the exact defect class recorded in the P3.4 verification lesson |
| D6 | The ruleset payload is **checked into the repository** | The ruleset is currently invisible to review, undiffable, and reconstructible only from the API. Storing it makes the gate reviewable like the rest of the CI configuration |

## Design

### 1. `maven.yml` restructure

Delete `paths-ignore` from the **`pull_request`** trigger only. The `push` trigger
keeps its `paths-ignore` — push runs are informational and gate nothing.

Add a `changes` job using `dorny/paths-filter@v4` — already the established pattern
in this repository (`.github/workflows/build-images.yml:39`) — expressed as
negations under `predicate-quantifier: every`, so `code` is true for any change that
is **not** exclusively documentation:

```yaml
  changes:
    runs-on: ubuntu-latest
    outputs:
      code: ${{ steps.filter.outputs.code }}
    steps:
      - uses: actions/checkout@v7
      - uses: dorny/paths-filter@v4
        id: filter
        with:
          predicate-quantifier: 'every'
          filters: |
            code:
              - '!docs/**'
              - '!documentation/**'
              - '!helm/**'
              - '!**/*.md'
              - '!.github/workflows/build-images.yml'
```

The exact negation/quantifier semantics of `dorny/paths-filter@v4` **must be
verified against its documentation and proven by test P2/P3 below** before this is
relied on; the implementation plan owns that verification. If the quantifier does
not behave as required, the fallback is to compute the flag in a `run:` step from
`git diff --name-only` against the PR base, keeping the same fail-closed semantics.

`build` and `code-quality` become conditional:

```yaml
  build:
    needs: changes
    if: needs.changes.outputs.code == 'true'
    ...
  code-quality:
    needs: changes
    if: needs.changes.outputs.code == 'true'
    ...
```

Add the aggregator, which is the one check the ruleset will require:

```yaml
  ci-gate:
    name: ci-gate
    if: always()
    needs: [changes, build, code-quality]
    runs-on: ubuntu-latest
    steps:
      - name: Check upstream job results
        run: |
          echo "results: ${{ join(needs.*.result, ',') }}"
          [[ "${{ contains(needs.*.result, 'failure') }}"   == "false" ]] || exit 1
          [[ "${{ contains(needs.*.result, 'cancelled') }}" == "false" ]] || exit 1
```

Semantics:

- `skipped` passes — that is the docs-only path, and the whole point of the design;
- `failure` and `cancelled` fail;
- `changes` is included in `needs` so that a failure of the filter job itself fails
  the gate, rather than skipping `build` and reporting green.

`ci-gate` runs on every PR to `main` without exception, so it always reports a
conclusion and can never deadlock a PR.

### 2. Ruleset change

Add one rule to ruleset `15118295`:

```json
{
  "type": "required_status_checks",
  "parameters": {
    "strict_required_status_checks_policy": false,
    "do_not_enforce_on_create": false,
    "required_status_checks": [
      { "context": "ci-gate" },
      { "context": "trufflehog" }
    ]
  }
}
```

and set `bypass_actors` to the repository **admin** role in `pull_request` mode:

```json
"bypass_actors": [
  { "actor_id": <admin-role-id>, "actor_type": "RepositoryRole", "bypass_mode": "pull_request" }
]
```

`<admin-role-id>` is **not assumed**: the implementation plan resolves it from
`gh api repos/theyellow/ecip/rulesets/rule-suites` / the roles API before writing
the payload.

`integration_id` is deliberately omitted from each context so any app may report it;
both checks come from GitHub Actions.

### 3. Ruleset as code

- `.github/rulesets/main.json` — the full ruleset payload, the source of truth.
- `docs/operations/branch-protection.md` — what is required and why, the apply
  command, and the outage procedure:

```bash
# apply
gh api --method PUT repos/theyellow/ecip/rulesets/15118295 --input .github/rulesets/main.json

# outage escape hatch (preferred over standing bypass)
gh api --method PUT repos/theyellow/ecip/rulesets/15118295 -f enforcement=evaluate
# ... and back to 'active' immediately afterwards
```

### 4. Sequencing

Strict order — requiring a context that has never reported would deadlock the very
PR that introduces it:

1. PR A: the `maven.yml` restructure. Merges under today's (ungated) rules. After
   merge, `ci-gate` exists as a reported check name.
2. The payload is authored on PR B's branch and applied to the live ruleset via the
   API from there, so the file and the live state are identical before the file
   lands on `main`.
3. PR B: `.github/rulesets/main.json`, `docs/operations/branch-protection.md`,
   ROADMAP/BACKLOG updates. This PR is itself the first one to merge *through* the
   new gate, and doubles as proof P2 (docs-only path).

## Proof that the gate can fail

P3.4 shipped three checks that could not fail. Every proof below must be **observed
and recorded in the PR description**, not assumed:

| # | Proof | Expected |
|---|---|---|
| P1 | Throwaway branch with a deliberately failing unit test, opened as a PR | `build` red → `ci-gate` red → merge button **blocked** with `ci-gate` listed under Required |
| P2 | Docs-only PR (e.g. a `ROADMAP.md` edit) | `changes` runs, `build` + `code-quality` **skipped**, `ci-gate` green in well under a minute, PR mergeable |
| P3 | Change one file in a path not named in the ignore list (e.g. a new top-level directory) | `code == 'true'`, full build runs — filter is fail-closed |
| P4 | Inspect the merge box on any PR | `trufflehog` appears under Required |

P4 is a **weaker proof** than P1–P3 and is labelled as such: it confirms the check
is required, not that a verified secret would actually block a merge. Deliberately
committing a live credential to prove that is not an acceptable test, and TruffleHog
only flags *verified* secrets, so a dummy value would not trigger it. The residual
gap is accepted and recorded here rather than papered over.

## Out of scope

- **`code-quality` duplicates `build`.** `build` already runs `spotless:check` and
  `pmd:check` (`maven.yml:62-66`), and `code-quality` runs an additional
  `clean install -DskipTests` to do the same two things again. Real waste, but
  removing it is a separate change with its own risk; filed to `BACKLOG.md` rather
  than bundled here.
- Requiring `Analyze Java` (CodeQL) — see D2.
- Merge queues — see D3.
- P3.5 (Gatling load tests in CI). If 3.5 lands later, its job joins `ci-gate`'s
  `needs` list rather than becoming a second required context.
