## Verify-first: what the code ACTUALLY looks like today (2026-07-27)

The 2026-07-18 finding is **partially stale** — confirm each point against `main` before
implementing (this is the roadmap's standing rule; P1 discarded a whole batch for skipping it).

1. **Scheme whitelist ALREADY EXISTS** — `DocumentIngestionController.ingestUrl()`
   (`.../controller/DocumentIngestionController.java:48-60`) rejects blank URLs and any scheme
   that is not `http`/`https`. So RT2-005's `file:///etc/passwd` and "accepts any scheme"
   examples are **already closed at the controller boundary.** Do not re-report these as open.

2. **The real open gaps** (all in `.../service/DocumentIngestionService.java`):
   - `fetchWithTimeout(String url)` (`:320-341`) does **zero** validation — `URI.create(url)`
     → `HttpClient.send(...)`. No private-IP / loopback / link-local / metadata-IP blocklist,
     no DNS-resolution check. This is where the finding's recommended defense-in-depth belongs.
   - Live vectors still open: `http://localhost:<port>/...` (internal services),
     `http://169.254.169.254/...` (cloud metadata), and **DNS rebinding** (host resolves to a
     public IP at validation time, `127.0.0.1` at connect time).

3. **Redirect policy is `Redirect.NEVER`** — `HttpClient.newBuilder()` default (`:321`). A 302
   to an internal host is NOT followed today, so redirect-based bypass is currently closed.
   The design must **keep it NEVER**, or, if it ever changes, re-validate every hop.

4. **Bypass path:** `reprocessJob` (`:241`) calls `submitUrlIngestion(oldJob.getSourceRef(), …)`
   directly, **skipping the controller scheme check.** Any validation added only at the
   controller would not cover reprocessing. → argues for putting the guard in the service.

5. **Adjacent surface, OUT OF SCOPE:** the 13 `connector/impl/*Connector.java` fetchers also
   make outbound HTTP, but to operator-configured / hardcoded API endpoints, not user-submitted
   URLs. Note as related; do not expand P2.2 to cover them unless the brainstorm decides to.

Existing guardrails already on this path (keep, don't duplicate): `FETCH_TIMEOUT = 30s`
(`:58`), `MAX_CONTENT_BYTES = 10 MB` (`:57`, enforced `:331`), injection-pattern scan on
extracted text (`:277`).

## Scope for P2.2

Add SSRF defense-in-depth to the **URL document-ingestion path**, primarily at the service
layer so it also covers the reprocess bypass:

- scheme allow-list (`http`/`https`) — mirror/centralize the existing controller check;
- resolve the host and **reject** loopback (`127.0.0.0/8`, `::1`), RFC-1918
  (`10/8`, `172.16/12`, `192.168/16`), link-local (`169.254/16`, `fe80::/10`), the AWS/GCP/Azure
  metadata IP (`169.254.169.254`), wildcard/`0.0.0.0`, and multicast/reserved ranges;
- close the DNS-rebinding TOCTOU (see open questions);
- keep redirects `NEVER`;
- fail the job cleanly (`FAILED` with a clear reason) rather than throwing raw.

## Open design questions for the brainstorm (do NOT pre-decide)

1. **DNS-rebinding TOCTOU** — the hard one. `java.net.http.HttpClient` re-resolves DNS at
   connect time, so "resolve → validate → `HttpClient.send`" leaves a gap. Options to weigh:
   (a) resolve, validate **all** A/AAAA records, then connect to the **pinned** validated IP
   with the original `Host` header preserved (awkward with `HttpClient` — may need a custom
   `ProxySelector`/socket or a small manual connect); (b) accept the residual TOCTOU risk given
   redirects are off and the fetch is a one-shot GET, and document it; (c) swap to a client that
   allows an address-resolver hook. Pick deliberately.
2. **Where does the guard live?** A reusable `emcip-core` util (other services may need SSRF
   guarding later — e.g. any future webhook/callback feature) vs. a knowledge-engine-local
   helper. Core has no SSRF util today (checked). Lean core-ward only if a second caller is real.
3. **Allow-list escape hatch?** Do operators ever need to ingest from an internal/private host
   on purpose (e.g. an internal wiki)? If yes, a configurable allow-list of permitted hosts/CIDRs
   is needed; if no, keep it strictly deny-private.
4. **IPv6 completeness** — IPv4-mapped IPv6 (`::ffff:127.0.0.1`), NAT64, etc. Decide how far to go.
5. **Config surface** — timeouts/limits are hardcoded constants today; does the blocklist need to
   be config-driven or is a hardcoded constant set fine for 1.0.0?

## Acceptance criteria (draft — refine in spec)

- A URL resolving to any blocked range is rejected **before any socket connect**; job ends
  `FAILED` with a reason naming the blocked target class (not the raw internal response).
- `http://169.254.169.254/...`, `http://localhost/...`, `http://127.0.0.1/...`,
  `http://10.x/`, `http://192.168.x/` are all rejected.
- Legitimate public URLs still ingest (regression: keep an existing happy-path test green).
- The reprocess path (`reprocessJob`) is covered by the same guard.
- Redirects remain disabled.

## Test sketch

- Unit tests on the SSRF-guard util: table of (input host/IP → allowed|blocked) covering each
  range above, IPv4 + IPv6 + IPv4-mapped, and hostname-that-resolves-to-private (use a fixed
  resolver/stub, not real DNS).
- Service test: submit a blocked URL → job `FAILED`; submit an allowed URL (stub the HTTP
  fetch) → proceeds. Reuse the AGE-enabled Testcontainers harness now wired in
  (`TestcontainersInitializer`) if a DB context is needed.
- Guard against DNS-rebinding in a test only if option (a) is chosen (assert connect targets the
  pinned IP).
