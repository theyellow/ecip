# P3.6 — Per-user / per-IP rate limiting (and trusted client IP)

**Date**: 2026-08-08
**Roadmap item**: P3.6 (`documentation/ROADMAP.md`, tier ② Security) — ID `RT-F1`
**Also closes**: P2.8-F1 (XFF trusted-proxy allow-list), `docs/superpowers/BACKLOG.md` §0b
**Status**: design approved, pending implementation plan

---

## Problem

`emcip-admin-api` has three Resilience4j rate limiters
(`emcip-admin-api/src/main/resources/application.yml:85-98`):

| Instance | Limit | Applied at |
|---|---|---|
| `auth` | 10 / 60s | `AuthController:47,56` (token, refresh) |
| `llm-trigger` | 20 / 60s | `FlagController:118,138`, `SimulateController:39` |
| `admin-crud` | 100 / 60s | `TenantController:51,62,73` |

Each named instance is **one global counter**. Every caller draws from the same
bucket, so a single user — or a single attacker — exhausts the quota for everyone.
Ten failed logins per minute across the entire deployment is also far too coarse to
be useful as brute-force protection: it cannot distinguish one attacker from ten
legitimate users mistyping passwords, and it denies service to all of them equally.

Coverage is also incidental rather than designed. The limiter is applied by hand at
each call site with `RateLimiterOperator`, so an endpoint is limited only if someone
remembered. `FlagController:83` (`POST /api/flags/{id}/reply`) has no limiter at all;
nothing reports this.

## The dependency that shapes the design

Per-IP limiting requires a client IP the attacker cannot choose. Today the
application has none.

`ClientIp.resolve` (`emcip-admin-api/src/main/java/io/emcip/admin/api/util/ClientIp.java:18-22`)
takes the **leftmost** `X-Forwarded-For` token. Its own javadoc says XFF is only
trustworthy behind a trusted proxy and points at open item P2.8-F1. The BFF
(`emcip-admin-ui/.../ApiProxyController.java:59-70`) forwards every non-hop-by-hop
header verbatim — including a client-supplied `X-Forwarded-For` — and appends no hop
of its own.

So unless something upstream sanitises the header, `X-Forwarded-For: <random>` on
each request defeats a per-IP limiter entirely. Whether the nginx ingress saves us
depends on its `use-forwarded-headers` setting, which `helm/emcip/values.yaml` does
not configure. **That behaviour is unverified and this design does not rely on it.**

A limiter an attacker steps around with one header is worse than no limiter, because
it appears in the runbook as protection. Per-IP limiting and trusted-IP resolution
are therefore one piece of work, not two.

## Decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | Trusted IP by **hop count from the right** of `X-Forwarded-For`, config `emcip.security.trusted-proxy-hops` | Attacker-prepended entries land to the left and are ignored no matter how many are added. No CIDR list to maintain as pod IPs churn |
| D2 | The **BFF appends its own hop** instead of forwarding headers verbatim | Makes the hop count deterministic and independent of nginx's `use-forwarded-headers` mode |
| D3 | A single **`RateLimitWebFilter`**, not per-controller operators | Coverage becomes structural rather than a thing to remember. `/api/**` catch-all means a new endpoint is limited by default |
| D4 | Per-key `RateLimiter` instances held in a **Caffeine cache**, not the Resilience4j registry | The registry has no eviction; a rotating-key attack would grow it without bound — turning a DoS control into a DoS vector |
| D5 | Keep the three existing `application.yml` instances as **config templates** | Limits stay configurable in the same place, operators see no new config shape |
| D6 | **In-process** counters, no Redis | Correct at `replicas: 1`, which is every service today. Same caveat and same eventual fix as P1-M2 (per-replica JWT revocation) |
| D7 | `/api/internal/**` and `/actuator/**` are **exempt** | Inter-service calls; throttling them risks cascading failure rather than preventing abuse |

## Design

### 1. Trusted client IP

New `TrustedClientIp` component in `emcip-admin-api`, replacing `ClientIp`'s
resolution logic (the `Resolved(ip, source)` record shape is kept — P2.8's audit path
consumes it).

```
X-Forwarded-For: 9.9.9.9, 203.0.113.7, 10.42.0.5
                 ^spoofed  ^real client ^BFF hop

trusted-proxy-hops: 2   →  2nd from the right  →  203.0.113.7
```

Rules:

- Take the entry `trusted-proxy-hops` positions from the right (1 = rightmost).
- **Fewer entries than hops → do not guess.** Fall back to the socket address, tag
  the source as untrusted, and increment a counter metric. A topology change then
  shows up in metrics instead of silently selecting an attacker-controlled entry.
- Malformed entries (not a parseable IP) are treated the same way.
- `source` remains a tag on the result: `XFF_TRUSTED` / `SOCKET` / `UNKNOWN`.

With D2 in place, `trusted-proxy-hops: 2` is correct under **either** nginx mode,
which is why the unverified ingress setting stops mattering:

| nginx `use-forwarded-headers` | XFF reaching admin-api | 2nd from right |
|---|---|---|
| `false` (replaces with `$remote_addr`) | `203.0.113.7, <bff>` | `203.0.113.7` ✓ |
| `true` (appends to client value) | `9.9.9.9, 203.0.113.7, <bff>` | `203.0.113.7` ✓ |

`trusted-proxy-hops` is still **verified against a live request** before being fixed, not
assumed from the topology diagram (see Proof, below). No default that silently works:
the property is required, and startup fails without it.

The BFF (`ApiProxyController`) is changed to strip inbound `X-Forwarded-For` /
`Forwarded` and set `X-Forwarded-For` to `<inbound XFF>, <its own remote address>` —
i.e. it appends a hop the way a proxy is supposed to.

This makes the P2.8 login-audit IP trustworthy as a side effect, which closes P2.8-F1.

### 2. `RateLimitWebFilter`

A `WebFilter` registered with
`.addFilterAfter(rateLimitFilter, SecurityWebFiltersOrder.AUTHENTICATION)` in
`SecurityConfig` — the same placement `AdminTenantContextFilter` already uses
(`SecurityConfig.java:135`), so the principal is resolved when the filter runs.

Group resolution, first match wins:

| Order | Path | Group | Key |
|---|---|---|---|
| 1 | `/actuator/**`, `/api/internal/**` | *(exempt)* | — |
| 2 | `/api/auth/**`, `/auth/token` | `auth` (10/60s) | trusted client IP |
| 3 | `POST /api/flags/*/analyse`, `POST /api/flags/*/chat`, `POST /api/simulate/message` | `llm-trigger` (20/60s) | JWT subject |
| 4 | `/api/**` | `admin-crud` (100/60s) | JWT subject, else trusted client IP |

Rule 4 is the point of the filter: `POST /api/flags/{id}/reply`, unlimited today,
becomes limited without anyone having to notice it exists.

Per-key limiters:

```java
Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterAccess(Duration.ofMinutes(2))   // ≈ 2× the 60s refresh period
    .build()
```

one cache per group, values built from the group's registry configuration so
`application.yml` stays the single place limits are set. Eviction while a key is idle
is safe: a limiter recreated after two idle minutes starts full, and the key had made
no requests in that window anyway.

The three controller-level `RateLimiterOperator` calls are **removed**, so exactly one
counter applies per request.

### 3. Rejection response

**`GlobalExceptionHandler` will not catch this.** It is a `@RestControllerAdvice`
(`GlobalExceptionHandler.java:114` maps `RequestNotPermitted` → 429), and a
`WebFilter` runs outside the handler chain, so an exception thrown there never reaches
it. Left unhandled, rejections would surface as 500s — the same shape as the AUTHZ-500
bug P3.3 uncovered, from the same cause.

The filter therefore writes the response itself: status **429**, `Retry-After` in
seconds, and a `ProblemDetail` body matching `GlobalExceptionHandler`'s existing
`"Rate limit exceeded"` shape so clients see one format.

The existing `RequestNotPermitted` handler stays — it is still reachable from the
circuit-breaker/limiter usage elsewhere and removing it is out of scope.

### 4. Observability

- `emcip.ratelimit.rejected{group}` — counter, incremented on each 429.
- `emcip.ratelimit.untrusted_ip{reason}` — counter, incremented when hop resolution
  falls back. A non-zero rate here means the proxy topology no longer matches
  `trusted-proxy-hops`, i.e. the IP keying has quietly stopped being meaningful.
- WARN log on rejection with group and key **type** (`ip` / `user`), plus the key
  itself for the `auth` group only — brute-force forensics need the IP, and P2.8's
  audit trail already records client IPs for login events.

## Proof

The failure mode here is a control that looks present and isn't, so each of these must
be observed failing before it passes:

| # | Test | Must show |
|---|---|---|
| T1 | Two requests, different spoofed leftmost XFF, same real client position | Same bucket — the second is rejected. Fails against the current leftmost-token resolver |
| T2 | User A exhausts `admin-crud`; user B requests | B succeeds. Fails against today's global counter |
| T3 | Rejection response | HTTP **429** with `Retry-After` and the ProblemDetail body — *not* 500. Fails if the filter relies on `GlobalExceptionHandler` |
| T4 | Cache bound | 20 000 distinct keys leave cache size ≤ `maximumSize` |
| T5 | `POST /api/flags/{id}/reply` | Limited under `admin-crud`. Fails today (no limiter) |
| T6 | Fewer XFF entries than `trusted-proxy-hops` | Falls back to socket, tagged untrusted, counter incremented — no attacker-controlled entry selected |
| T7 | Live verification | A real request through nginx → BFF → admin-api resolves to the actual client IP at the configured hop count. Done against the running cluster, not asserted from the diagram |

T7 is the one that cannot be replaced by a unit test: `trusted-proxy-hops` is a number
that will be *wrong* silently if the topology differs from the assumption, and T1–T6
would all still pass with a wrong value.

## Out of scope

- **Distributed limiting.** In-process is correct at `replicas: 1`. Documented next to
  P1-M2 (per-replica JWT revocation), which degrades on scale-out for the same reason
  and should be solved with it — before 3.21 (HA / multi-replica).
- **RFC 7239 `Forwarded` header.** Stripped by the BFF, not parsed.
- **Account lockout** after N failures — a separate control with its own DoS
  trade-offs (an attacker can lock a known username out on purpose).
- **NetworkPolicy** (3.20). Until it exists, an in-cluster caller can reach admin-api
  without traversing the BFF. Hop-count resolution degrades safely there (too few
  entries → socket address → the pod's real IP), which is why D1 beats the
  "BFF is the sole authority" alternative.
- Rate limiting in services other than admin-api.
